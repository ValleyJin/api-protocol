# CoAP — 초경량 IoT

## 무엇을 배우는가

CoAP는 "저사양 기기를 위한 HTTP"라고 부를 만하다. GET, PUT 같은 메서드가 있고 응답 코드도 HTTP를 닮았다. 다른 점은 전부 **작게 만드는** 쪽으로 기울어 있다.

| | HTTP/1.1 | CoAP |
|---|---|---|
| 자료 | 텍스트 | 바이너리 |
| 아래 계층 | TCP | UDP |
| 헤더 | 수백 바이트 | **4바이트** |
| 재전송 | TCP가 한다 | CoAP가 직접 한다 |

헤더가 4바이트다. HTTP의 `GET / HTTP/1.1\r\n` 한 줄보다 짧다.

```
 0                   1                   2                   3
┌───┬───┬───────┬───────────────┬───────────────────────────────┐
│Ver│ T │  TKL  │     Code      │        Message ID (16)        │
└───┴───┴───────┴───────────────┴───────────────────────────────┘
  2   2     4           8                      16                  = 32비트
```

- `Ver` 항상 1
- `T` 메시지 종류. 0=CON(확인 받겠다) 1=NON(안 받겠다) 2=ACK 3=RST
- `TKL` 토큰 길이. 요청과 응답을 짝지을 때 쓴다
- `Code` 상위 3비트가 부류, 하위 5비트가 세부. `0.01`=GET, `2.05`=Content

### UDP를 골랐으니 떠안는 일

TCP가 없으니 언제 몇 번 다시 보낼지를 CoAP가 스스로 정해야 한다. CON으로 보내면 상대가 ACK를 줄 때까지 2초, 4초, 8초, 16초로 늘려 가며 최대 네 번 다시 보낸다(RFC 7252 기본값). NON으로 보내면 한 번 보내고 만다.

03 폴더에서 TCP가 대신 해 주던 일을 여기서는 직접 적는다. `client.py`의 `send_confirmable()`이 그 일을 한다.

### 옵션 — 델타로 적는다

경로나 콘텐츠 형식 같은 부가 정보를 옵션으로 적는다. 옵션 번호를 그대로 적지 않고 **앞 옵션과의 차이(델타)**만 적는다. 번호가 오름차순이어야 하는 까닭이다.

경로가 `/a/b`면 Uri-Path 옵션(번호 11)을 두 번 적는다. 두 번째는 델타가 0이라 옵션 번호를 다시 적지 않는다. 델타와 길이를 4비트씩 묶어 옵션 머리가 한 바이트로 끝난다. 여기서도 바이트를 아끼려는 설계가 보인다.

## 파일

| 파일 | 하는 일 |
|---|---|
| `coap.py` | CoAP 메시지를 만들고 읽는 최소 구현 |
| `server.py` | CoAP 서버. `--drop-ack`로 재전송을 볼 수 있다 |
| `client.py` | CON 재전송까지 직접 구현한 클라이언트 |

`aiocoap`을 깔지 않아도 된다.

## 만들 것

- CoAP 서버와 클라이언트
- 같은 리소스를 HTTP로도 열어 두고 메시지 크기를 견주는 스크립트
- Observe 옵션으로 값이 바뀔 때 알림을 받는 구현

## 확인하는 법

### 1. 돌려 본다

```
python3 server.py                     # 창 하나
python3 client.py get                 # 다른 창
python3 client.py put 23.5
```

보내는 메시지를 16진수로 찍는다. 4바이트 헤더 뒤에 토큰, 옵션, 본문이 어떻게 붙는지 확인한다.

### 2. HTTP와 견준다

```
python3 client.py get --compare
```

### 3. 재전송을 본다

```
python3 server.py --drop-ack          # ACK를 일부러 안 보낸다
python3 client.py get
```

2초, 4초, 8초, 16초로 늘려 가며 네 번 다시 보내고 포기한다.

**서버를 그냥 내려도 이 클라이언트에서는 재전송이 그대로 보인다.** 커널이 ICMP port unreachable을 돌려주지만, `connect()`하지 않은 UDP 소켓에는 그 오류가 전달되지 않기 때문이다. 소켓을 `connect()`하는 구현이라면 RFC 7252 4.2절대로 재전송을 일찍 포기한다. 어느 쪽이든 재전송 실습은 서버가 살아 있되 답을 안 하는 쪽이 뜻이 분명하다.

### 4. NON과 견준다

```
python3 server.py --drop-ack
python3 client.py get --non
```

한 번 보내고 끝난다. `--drop-ack`는 CON의 ACK만 막으므로 NON에는 서버가 답을 준다. 다른 점은 재전송이 없다는 것이다. 답이 안 와도 다시 보내지 않으니, 잃어버려도 아무도 모른다.

### 5. 유실과 재정렬을 일부러 만든다

루프백에서는 저절로 일어나지 않는다. 도구로 만들어야 한다. 어느 쪽이든 관리자 권한이 필요하다.

```
# macOS
sudo dnctl pipe 1 config plr 0.3 delay 50
sudo pfctl -f - <<< "dummynet in proto udp from any to any port 5683 pipe 1"

# 리눅스
sudo tc qdisc add dev lo root netem loss 30% delay 50ms reorder 25%
```

도구가 없으면 클라이언트 코드에서 보내는 패킷을 일정 확률로 버린다.

## 실제로 재어 본 값

```
CON GET  요청 38바이트 (헤더 4 + 토큰 2 + 옵션 32)
ACK 2.05 응답 83바이트 (본문 74)
ACK 2.04 응답  6바이트 (본문 없음)

같은 값을 받는 데 든 바이트
  CoAP  요청  38 + 응답  83 = 규약이 쓴 바이트 47
  HTTP  요청 120 + 응답 199 = 규약이 쓴 바이트 245
```

옵션 32바이트가 요청의 대부분이다. 경로가 `/sensors/living-room/temperature`로 길기 때문이다. MQTT에서 주제 이름이 그랬던 것과 같다. 경로를 `/s/lr/t`로 줄이면 요청이 크게 줄어든다. 좁은 망에서는 이런 것까지 따진다.

## 자주 막히는 곳

| 증상 | 까닭 |
|---|---|
| 재전송이 안 보인다 | 서버가 ACK를 돌려주고 있다. `--drop-ack`로 띄운다 |
| 응답이 안 온다 | 포트 5683이 이미 쓰이고 있을 수 있다. `--port`로 바꾼다 |
| 옵션 파싱이 깨진다 | 델타를 누적하지 않았다. 번호는 상대값이다 |

## 자료

RFC 7252. 특히 4.2절(재전송)과 5.10절(옵션)이 이 폴더와 맞닿아 있다.
