# WebSocket — 양방향 상시 연결

## 무엇을 배우는가

WebSocket은 HTTP로 시작해 HTTP를 버린다. 처음 한 번은 평범한 HTTP 요청을 보내되 "이 연결을 WebSocket으로 바꿔 달라"고 적는다. 서버가 101로 답하면 그때부터 **같은 TCP 연결 위에서** 프레임을 주고받는다.

```
클라이언트 → GET /ws HTTP/1.1
             Upgrade: websocket
             Sec-WebSocket-Key: <무작위 16바이트를 base64로>

서버      → HTTP/1.1 101 Switching Protocols
             Upgrade: websocket
             Sec-WebSocket-Accept: base64(sha1(key + 고정 GUID))
```

Accept 값을 계산해 돌려주는 것은 암호를 걸려는 것이 아니라 **확인**을 하려는 것이다. 중간의 캐시 서버가 아무 생각 없이 101을 흉내 내는 일을 막으려는 장치다. GUID `258EAFA5-E914-47DA-95CA-C5AB0DC85B11`은 RFC 6455가 못 박은 값이다.

### 프레임

```
┌─┬─┬─┬─┬───────┬─┬─────────┬─────────────┬──────────┐
│F│R│R│R│ opcode│M│ 길이(7) │ 확장 길이   │ 마스크키 │ + 본문
│I│S│S│S│  (4)  │A│         │ (0/2/8바이트)│(0/4바이트)│
│N│V│V│V│       │S│         │             │          │
└─┴─┴─┴─┴───────┴─┴─────────┴─────────────┴──────────┘
```

길이 필드가 3단이다. 125까지는 7비트에 그대로 적고, 126이면 뒤에 2바이트, 127이면 8바이트를 더 읽는다. 짧은 메시지를 짧게 적으려는 설계다. **짧은 메시지의 프레임 헤더는 2바이트**다. HTTP 헤더 수백 바이트와 견줘 볼 만하다.

### 마스킹 — 암호가 아니다

클라이언트가 보내는 프레임은 반드시 마스킹한다. 본문 각 바이트를 4바이트 마스크 키와 XOR한다. 키를 그 자리에 함께 실어 보내므로 암호로서는 아무 쓸모가 없다.

까닭은 다른 데 있다. 중간의 낡은 프록시가 프레임 본문을 HTTP 요청으로 잘못 읽고 엉뚱한 응답을 캐시에 넣는 일(cache poisoning)을 막으려고 넣은 장치다. 프레임마다 다른 키로 XOR해 두면 공격자가 본문을 HTTP 요청처럼 보이게 만들 수 없다.

서버가 보내는 프레임은 마스킹하지 않는다.

## 파일

| 파일 | 하는 일 |
|---|---|
| `ws.py` | 프레임과 핸드셰이크를 만들고 읽는 최소 구현 |
| `server.py` | 핸드셰이크를 받고 값을 밀어 주는 서버 |
| `raw_client.py` | 핸드셰이크와 프레임을 손으로 만드는 클라이언트 |

## 만들 것

- HTTP Upgrade 핸드셰이크를 직접 주고받는 최소 클라이언트
- 프레임 헤더(FIN, opcode, mask, payload length)를 조립하고 해석하는 코드
- 같은 일을 `websockets` 같은 라이브러리로 다시 구현

## 확인하는 법

### 1. 돌려 본다

```
python3 server.py                     # 창 하나
python3 raw_client.py --count 3       # 창 둘
```

클라이언트가 계산한 Accept 값과 서버가 보낸 값이 같은지 확인한다. 다르면 연결을 끊어야 한다.

### 2. 서버가 먼저 말을 거는 것을 본다

앞의 두 프로토콜에서는 값을 알고 싶으면 클라이언트가 물어야 했다. 여기서는 값이 바뀌면 서버가 밀어 준다. 요청은 핸드셰이크 한 번뿐이다.

```
python3 server.py --interval 0.3
python3 raw_client.py --count 10
```

### 3. 마스킹을 확인한다

```
python3 raw_client.py --send '{"set":24.0}' --count 1
```

클라이언트가 보낸 프레임에 마스크 키 4바이트가 그냥 붙는다. 12바이트 본문에 헤더 2와 마스크 키 4, 모두 6바이트가 얹힌다. 짧은 메시지일수록 비율이 크다.

서버 쪽 출력에서 `마스킹됨=True`가 뜨는 것을 확인한다. 서버가 보낸 프레임은 `마스킹됨=False`다.

### 4. 핸드셰이크와 프레임을 캡처로 견준다

```
sudo tcpdump -i lo0 -A -c 30 port 8081
```

핸드셰이크는 글자로 읽힌다. 서버 프레임은 앞 2바이트 헤더만 바이너리고 본문 JSON은 그대로 읽히는데, 클라이언트가 보낸 프레임은 마스킹돼 본문이 글자로 읽히지 않는다. 같은 연결 안에서 프로토콜이 바뀌는 지점이 눈에 보인다.

## 실제로 재어 본 값

```
핸드셰이크 요청 155바이트 + 응답 129바이트 = 284바이트 (연결마다 한 번)
값 한 건 프레임 76바이트 = 헤더 2 + 본문 74
클라이언트가 12바이트를 보낼 때 18바이트 = 헤더 2 + 마스크키 4 + 본문 12
```

284는 기본 포트 8081에서 잰 값이다. `Host` 헤더가 포트 자릿수를 따라가니 포트를 다섯 자리로 바꾸면 요청이 156바이트가 되어 285가 된다. 본문 74도 `ts`의 끝자리에 따라 흔들린다. 서버를 서른 번 새로 띄워 재니 프레임이 76바이트 스물여덟 번, 75바이트 두 번이었다. 숫자를 외우지 말고 돌려서 나온 값을 읽는다.

HTTP로 같은 값을 받으면 매번 요청 120 + 응답 199바이트다. 핸드셰이크 284바이트를 미리 냈으니 **두 번째 값부터 이득**이다. 한 건만 받으면 360 대 319로 손해고, 두 건이면 436 대 638로 이득이다. 경계는 핸드셰이크가 282든 284든 둘째 값이다. 값이 자주 바뀌고 연결이 오래 이어질수록 유리해진다.

대신 연결을 계속 붙들고 있어야 한다. 서버가 동시 연결 수만큼 자원을 쓴다. 클라이언트가 아주 많고 값이 드물게 바뀌면 손해일 수도 있다.

## 자주 막히는 곳

| 증상 | 까닭 |
|---|---|
| 101이 아니라 400이 온다 | `Upgrade: websocket` 헤더나 `Sec-WebSocket-Key`가 빠졌다 |
| 서버가 프레임을 못 읽는다 | 클라이언트가 마스킹을 안 했다. 프로토콜 위반이다 |
| 프레임이 중간에 잘려 보인다 | TCP가 나눠 준 것이다. 길이 필드를 보고 다 올 때까지 모아야 한다 |
| 큰 메시지를 엉뚱하게 읽는다 | 길이가 126 이상이면 확장 길이 필드를 읽어야 한다 |
