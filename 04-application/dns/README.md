# DNS — 요청-응답 (이름 풀이)

## 무엇을 배우는가

DNS는 UDP 한 통에 질의와 응답을 담는 바이너리 프로토콜이다. 글자로 적는 HTTP와 달리 자리마다 뜻이 정해져 있어, 바이트를 세어 가며 읽어야 한다.

DNS 메시지는 12바이트 헤더로 시작한다.

```
┌────────────────┬────────────────┐
│    ID (16)     │   플래그 (16)  │
├────────────────┼────────────────┤
│  QDCOUNT (16)  │  ANCOUNT (16)  │   질문 개수 / 답 개수
├────────────────┼────────────────┤
│  NSCOUNT (16)  │  ARCOUNT (16)  │   권한 개수 / 추가 개수
└────────────────┴────────────────┘
```

이름은 점으로 잇지 않는다. '길이 + 글자'를 되풀이해 적는다.

```
example.com  →  \x07example\x03com\x00
```

### 이름 압축 — 파싱이 까다로운 진짜 까닭

같은 이름이 응답 안에 여러 번 나오면, 두 번째부터는 앞의 위치를 가리키는 2바이트 포인터로 줄인다. 맨 앞 두 비트가 `11`이면 포인터다. 좁은 UDP 한 통에 답을 최대한 담으려는 설계다.

그래서 이름을 읽다가 포인터를 만나면 그 자리로 건너뛰어 이어 읽고, 그 뒤에는 **포인터 바로 뒤로 돌아와야** 한다. `query.py`의 `decode_name()`이 이것을 다룬다. 포인터가 서로를 가리키는 고장 난 응답을 만나도 무한 루프에 빠지지 않도록 막아 둔다.

### UDP만 쓴다는 말은 반쪽이다

응답이 너무 커서 UDP 한 통에 담기지 않으면 서버가 답을 자르고 **TC 비트**를 세운다. 그러면 리졸버가 같은 질의를 TCP로 다시 보낸다. TCP에서는 앞에 2바이트 길이를 붙인다.

한계값은 EDNS0가 정한다. 질의를 보내는 쪽이 추가 구역에 OPT 레코드를 넣어 "나는 UDP로 이만큼까지 받을 수 있다"라고 알린다. 이 값이 작으면 잘린다.

## 파일

| 파일 | 하는 일 |
|---|---|
| `query.py` | 질의 패킷을 바이트로 조립하고 응답을 손으로 파싱한다 |
| `resolve_lib.py` | 같은 일을 운영체제에 맡기고 견준다 |

## 만들 것

- DNS 질의 패킷을 바이트로 직접 조립해 보내는 클라이언트
- 응답의 답 구역을 파싱해 A 레코드를 뽑는 파서
- 같은 일을 `socket.getaddrinfo`로 다시 구현

## 확인하는 법

### 1. `dig`로 먼저 본다

```
dig example.com
```

### 2. 직접 만든 질의를 보낸다

```
python3 query.py example.com
python3 query.py example.com --type AAAA --server 1.1.1.1
python3 query.py google.com --type MX
```

보내는 바이트를 16진수로 찍는다. `\x07example\x03com\x00`이 그대로 보인다.

### 3. TC 비트를 세워 TCP 대체를 본다

```
python3 query.py org --type DNSKEY --dnssec --bufsize 512
```

EDNS0 버퍼를 512로 낮추면 TC 비트가 서고, 코드가 곧바로 TCP로 다시 물어 1319바이트를 받아 온다.

1번에서 쓴 `dig`는 판본마다 기본 버퍼가 다르다. BIND 9.18 이상은 기본이 1232라 이 응답은 `dig`의 기본값으로도 잘린다. 그때는 `query.py`를 `--bufsize 4096`으로 돌려 잘리지 않는 응답과 견준다. `--bufsize`는 `query.py`의 옵션이고 `dig`는 이 꼴을 모른다(`dig`에서는 `+bufsize=4096`으로 쓴다).

`--type ANY`로는 이 실습이 안 된다. RFC 8482 때문에 요즘 공개 리졸버가 ANY 질의에 큰 응답을 주지 않는다.

### 4. 운영체제에 맡겨 본다

```
python3 resolve_lib.py example.com
```

`socket.getaddrinfo()` 한 줄 안에서 운영체제가 `/etc/hosts`를 확인하고, 캐시를 뒤지고, 검색 도메인을 붙이고, IPv4/IPv6 우선순위(RFC 6724)를 매기는 일을 모두 한다.

DNS는 4층 프로토콜이지만 **이름 풀이 API는 운영체제가 내준다.** 그래서 라이브러리를 깔지 않아도 이름을 풀 수 있다. [05-api-layers](../../05-api-layers/)에서 다룰 "API는 스택의 어디에 붙는가"라는 물음이 여기서 그대로 드러난다.

## 견줄 것

- **같은 이름을 두 번 물어본다.** 두 번째가 훨씬 빠르면 캐시에 걸린 것이다. TTL이 지나면 다시 느려진다.
- **응답 안의 포인터를 찾는다.** 답 구역의 이름은 첫 답부터 2바이트로 줄어 있다. 질문 구역에 이미 적힌 이름을 가리키기 때문이다. 그 2바이트가 `c0 0c`, 곧 헤더 12바이트 바로 뒤에서 질문 구역이 시작하는 오프셋 12를 가리키는 압축 포인터다. `query.py`의 `decode_name()`이 이것을 어떻게 따라가는지 함께 읽는다.
- **캡처를 떠서 포트를 본다.** `sudo tcpdump -i en0 -c 10 port 53`을 걸고 두 실습을 각각 돌리면, 직접 만든 질의는 8.8.8.8로 가고 `getaddrinfo`는 시스템에 설정된 리졸버로 가는 것이 보인다.

## 자주 막히는 곳

| 증상 | 까닭 |
|---|---|
| 답이 없다 | 방화벽이 53번 포트를 막았을 수 있다. 다른 `--server`로 해 본다 |
| TC 비트가 안 선다 | `--type ANY`를 쓰고 있다. RFC 8482로 막혔다. `DNSKEY`로 바꾼다 |
| 파싱이 깨진다 | 압축 포인터를 안 따라가고 있다. `decode_name()`을 다시 읽는다 |
