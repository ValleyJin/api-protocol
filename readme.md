# 🌐 통신 프로토콜 실습

통신 프로토콜을 계층별로 훑고 직접 돌려 보는 실습 교재다. 특정 프로토콜 하나를 깊게 파지 않고, 하드웨어에서 애플리케이션까지 스택 전체를 아래에서 위로 밟아 올라간다. 맨 위에서는 개발자가 만든 프로그램을 스택과 이어 주는 **API**를 여덟 가지 방식으로 하나씩 짜 보고 서로 견준다.

읽기만 하는 교재가 아니다. **모든 폴더에 돌아가는 코드가 있다.** 프레임 파서부터 MQTT 브로커, CoAP 서버, gRPC 서비스까지 직접 만들어 본다.

## 바로 시작하기

파이썬 3.9 이상만 있으면 된다. 외부 패키지는 gRPC 실습 하나에만 필요하다.

```bash
git clone https://github.com/ValleyJin/api-protocol.git
cd api-protocol

# 1층: 내 기기의 인터페이스와 MAC 주소를 본다
python3 01-link-layer/list_interfaces.py

# 2층: ICMP를 직접 만들어 보낸다
python3 02-internet-layer/ping.py 8.8.8.8

# 3층: 소켓 API만으로 서버와 클라이언트를 돌린다
python3 03-transport-socket/tcp_echo_server.py &
python3 03-transport-socket/tcp_echo_client.py --stream

# 3층: TCP와 UDP에 같은 일을 시켜 다섯 가지를 나란히 잰다
python3 03-transport-socket/compare_tcp_udp.py

# 4층: 직접 구현한 다섯 프로토콜 가운데 MQTT로 발행-구독을 해 본다 (브로커도 직접 만든 것이다)
python3 04-application/mqtt/broker.py &
python3 04-application/mqtt/publisher.py 23.5 --retain
python3 04-application/mqtt/subscriber.py --timeout 3

# API: 여덟 가지 가운데 여섯 가지를 한 표에 놓고 견준다
python3 05-api-layers/compare.py

# 인캡슐레이션: 헤더가 쌓이는 과정을 벗겨 본다
python3 06-encapsulation/peel.py 06-encapsulation/samples/sample.pcap
```

캡처를 뜨는 실습에는 관리자 권한이 필요하다. 권한이 없어도 `06-encapsulation/samples/sample.pcap`으로 파서를 익힐 수 있다.

## 하나의 과제를 끝까지 끌고 간다

프로토콜과 API를 견주려면 같은 일을 시켜야 한다. 이 교재는 과제 하나를 정해 두고 계층마다 되풀이한다.

**센서 값 하나를 올리고, 받는 쪽이 그 값을 읽는다.**

그 과제는 `04-application/common/sensor.py`와 `05-api-layers/common/store.py`에 한 번씩만 적어 두었고, 4층과 그 위를 다루는 폴더가 그것을 함께 쓴다. 그래서 "메시지 한 건이 몇 바이트인가"를 나란히 놓고 볼 수 있다.

실제로 돌려 재어 본 값이다.

| 방식 | 요청 | 응답 | 본문 | 규약이 쓴 바이트 |
|---|---|---|---|---|
| HTTP/1.1 | 120 | 199 | 74 | 245 |
| CoAP | 38 | 83 | 74 | 47 |
| MQTT PUBLISH | — | 36 | 4 | 32 |
| WebSocket 프레임 | — | 76 | 74 | 2 (핸드셰이크 284 별도) |
| gRPC (protobuf) | — | — | 34 | JSON 70바이트보다 51% 작다 |

**다섯 행이 다 같은 본문을 나른 것은 아니다.** HTTP, CoAP, WebSocket 세 행만
`04-application/common/sensor.py`의 `encode_json`이 내놓는 JSON을 나른다. 셋이 같은 본문을 쓰니
"규약이 쓴 바이트" 칸을 그대로 견줄 수 있다. MQTT 행은 같은 파일의 `encode_compact`를 쓴다.
온도를 글자로만 적는다. `reading()`이 18.0에서 26.0 사이를 뽑으니 이 표에서는 4바이트인데, 값에
매달린 길이다. `0.0`이면 3바이트, `100.0`이면 5바이트, `-100.0`이면 6바이트다. JSON이 74바이트를
쓰는 자리에 4바이트를 쓰니 MQTT의 32는 본문이 작은 탓도 있다. gRPC 행은
`05-api-layers/05-grpc-api`에서 잰 것이고, 견줄 대상이 74가 아니라 70바이트 JSON이다. 필드 이름이
`sensor`가 아니라 `id`라 네 바이트 짧다. 그래서 34를 위 세 행의 74와 빼거나 나누면 안 된다.

**74도 고정값이 아니다.** `ts`를 `round(time.time(), 3)`으로 적는데 끝자리가 0이면 JSON이 그 자리를
안 쓴다. 소수 세 자리가 남을 확률이 열에 아홉이니 본문도 열 번에 아홉 번쯤 74다. 실제로 재어 보면
74가 90.0%, 73이 9.1%, 72가 1.0%다(4000회, 0.3ms 간격). 간격을 10ms로 늘려도 90.4 / 8.7 / 0.9%로
같다. **재는 방법을 잘못 잡으면 흔들림이 안 보인다. 그리고 서버마다 다르다.** HTTP와 CoAP 서버는 띄울
때 값을 한 번 만들어 들고 있다(`STATE = {"latest": reading(21.0)}`). PUT으로 값을 올리면 그때 새로
만들지만, 그러지 않는 한 그대로다. gRPC는 `store.py`가 import할 때 `ts`를 정하고 `set_value()`가
불릴 때 다시 정한다. 이 셋은 가만히 두고 몇 번을 물어도 길이가 그대로이니, 흔들림을 보려면 서버를
새로 띄워야 한다.

**WebSocket은 가만히 둬도 흔들린다.** 서버가 `--interval`마다 `reading()`을 다시 부른다
(`server.py:75`). `--interval 0.05`로 띄워 프레임 150개를 받아 보니 76바이트가 133번, 75바이트가
15번, 74바이트가 2번이었다. **MQTT는 또 다르다.** publisher가 발행마다 `reading()`을 새로
만들지만 본문에는 `encode_compact`로 온도만 싣고 `ts`를 안 싣는다. 그래서 `ts`가 길이를 건드리지
못한다. 값을 주지 않고 서른 번 발행하니 PUBLISH가 서른 번 다 36바이트였다. `reading()`이 18.0에서 26.0 사이를 뽑아 온도 글자가 늘 넉 자이기 때문이다. 대신 **온도 글자가 길이를
끌고 간다.** `0.0`이면 35, `22.5`면 36, `100.0`과 `-40.0`이면 37, `1e300`이면 38바이트다.

그래도 "규약이 쓴 바이트" 칸은 245에서 안 움직인다. 본문이 한 바이트 줄면 응답도 한 바이트 줄고
`Content-Length`의 자릿수는 그대로이기 때문이다. HTTP 응답 헤더는 본문이 73이든 77이든 125바이트였다. 이 125는 HTTP 행만의 값이다. CoAP는 머리글에 9바이트(83 − 74), WebSocket 프레임은 2바이트를 쓴다.
**자릿수가 늘면 이 말이 틀어진다.** 다만 이 서버에서는 본문이 100바이트에 못 미친다. `reading()`이 온도를
`round(value, 1)`로 적고 그 글자가 가장 길어도 24자(`-1.2345678901234567e+300`)여서 본문이 최대
94바이트다. PUT으로 온도를 아무리 키워도 `Content-Length`는 두 자리로 남는다.

**gRPC 행의 70도 같이 흔들리고, 34는 안 흔들린다.** `05-api-layers/05-grpc-api`에서
`python3 client.py size`를 돌리면 두 길이를 나란히 찍는다. 까닭은 위와 같다. `store.py`의 `ts`가 소수
세 자리면 JSON이 70, 두 자리면 69, 한 자리면 68이다. 새 프로세스에서 300번 읽어 보니 70이 267번,
69가 31번, 68이 2번이었다. protobuf는 그 사이에 꿈쩍하지 않는다. 받은 바이트를 쪼개 보면
`0a 0b` + `living-room` 11 = 13, `11` + double 8 = 9, `1a 01` + `C` 1 = 3, `21` + double 8 = 9으로
합이 34다. `temperature`와 `ts`를 8바이트 double로 적으니 `inf`, `nan`, `1e308`, `5e-324`, `-1e308`을
넣어 봐도 다 34바이트다. **그래서 비율은 JSON 쪽이 정한다.** protobuf가 34일 때 `client.py`가 찍는
값은 JSON 70에서 51%, 69에서 51%, 68에서 50%다(34/70 = 51.43%, 34/69 = 50.72%, 34/68 = 50.00%).
68은 300번에 두 번이라 잘 안 보이지만 나온다.

**34가 고정인 것은 네 필드가 그대로일 때뿐이다.** proto3는 기본값인 필드를 아예 싣지 않는다.
`client.py set 0.0`을 하면 `temperature` 필드가 통째로 빠져 `11`과 double 8바이트, 모두 9바이트가
사라진다. 그때 protobuf는 25바이트이고 찍히는 비율도 63%나 64%가 된다. 서버를 스무 번 새로 띄워
재니 25는 스무 번 다 같고 비율은 64%가 대부분이었다. 둘 가운데 어느 쪽이 몇 번 나오는지는 돌릴
때마다 다르니 세지 않는다. `id`와 `unit`은 글자라 길이가 값을 그대로 따라간다. `id`를 빈 문자열로
만들면 21바이트, `unit`을 비우면 31바이트, 네 값이 모두 기본값이면 0바이트다.

**`0.0`과 `-0.0`이 갈리는 것도 눈여겨볼 만하다.** `temperature`를 `0.0`으로 두면 필드가 빠져
25바이트인데 `-0.0`으로 두면 34바이트 그대로다. protobuf가 기본값인지 따질 때 수의 크기가 아니라
바이트를 맞대기 때문이다. `0.0`은 `0000000000000000`이고 `-0.0`은 `0000000000000080`이라 서로 다르다.
`ts`도 같다. `ts`를 `0.0`으로 두면 25바이트, `-0.0`으로 두면 34바이트다. 고정 폭이라는 말은
`temperature`와 `ts` 두 필드를 두고 하는 말이지 메시지 전체를 두고 하는 말이 아니다. 자세한 것은
[05-api-layers/05-grpc-api](05-api-layers/05-grpc-api/)에 적어 두었다.

숫자를 곧이곧대로 읽으면 안 된다. 본문이 다르면 견줄 수 없고, 건수가 적으면 연결을 맺는 비용을 실제보다 크게 보게 된다. 어떤 조건에서 이 표의 순서가 뒤집히는지 직접 세어 보는 것이 이 교재의 실습이다. 어떻게 재고 어떻게 읽어야 하는지는 [06-encapsulation](06-encapsulation/)에 적어 두었다.

## 1. 이론(OSI 7계층)과 실제(TCP/IP 4계층)

OSI 7계층은 교과서의 모형이다. 실제 인터넷은 네 층으로 된 **TCP/IP 모델**로 돌아간다. 이 교재도 TCP/IP 4계층을 기준으로 삼는다.

```text
[ 이론: OSI 7계층 ]                 [ 실제: TCP/IP 4계층 ]             [ 역할과 대표 프로토콜 ]
7. 어플리케이션 (Application) ──┐
6. 프레젠테이션 (Presentation) ──┼─►  4층. 어플리케이션 계층  ───────► 소프트웨어 영역 (HTTP, MQTT)
5. 세션 (Session)             ──┘
─────────────────────────────────────────────────────────────────────────────────────────
4. 전송 (Transport)           ───►  3층. 전송 계층 (Transport) ──────► OS 엔진 영역 (TCP, UDP)
─────────────────────────────────────────────────────────────────────────────────────────
3. 네트워크 (Network)         ───►  2층. 인터넷 계층 (Internet) ─────► 주소·경로 영역 (IP)
─────────────────────────────────────────────────────────────────────────────────────────
2. 데이터 링크 (Data Link)    ──┐
1. 물리 (Physical)            ──┴─►  1층. 네트워크 인터페이스 계층 ──► 하드웨어 영역 (Wi-Fi, 이더넷)
```

'TCP/IP'는 프로토콜 두 개의 이름이 아니다. 인터넷 전체를 떠받치는 **프로토콜군(Suite)**의 이름이다. TCP/IP 모델은 OSI를 줄여서 만든 것이 아니다. OSI와 상관없이 따로 만든 모델이고, 오히려 OSI보다 먼저 나왔다. 세션과 프레젠테이션이 맡던 일, 곧 연결 상태를 관리하고 데이터 표현을 바꾸는 일은 애플리케이션 프로토콜과 라이브러리가 직접 한다.

## 2. 그래프로 본 IP와 TCP

* **📌 IP = 노드(Node):** 데이터가 닿아야 할 컴퓨터의 위치를 지정하고, 라우터마다 다음에 넘길 곳을 정해 그 컴퓨터까지 패킷을 보낸다. (Host-to-Host)
* **🔗 TCP = 엣지(Edge):** IP가 찾아낸 노드와 노드 사이에 신뢰할 수 있는 가상 파이프라인을 잇고, 흐름과 유실을 관리한다. 정작 데이터가 어느 경로로 가는지는 알지 못한다. (End-to-End)

> **요약:** IP가 노드를 찾아 그리로 패킷을 보내면, TCP가 그 양 끝 사이에 엣지를 잇는다. 그 위에서 HTTP나 MQTT 같은 애플리케이션 프로토콜이 데이터를 실어 나른다.

[02-internet-layer/traceroute.py](02-internet-layer/traceroute.py)를 돌려 IP가 경로를 미리 정하지 않는다는 사실을 눈으로 확인해 본다.

## 3. 애플리케이션 계층 프로토콜의 갈래

4층 프로토콜은 성격에 따라 여러 갈래로 갈린다. 무엇을 나르는지, 얼마나 가벼운지, 누가 먼저 말을 거는지가 그 기준이다.

* **요청-응답(Request-Response):** **HTTP** (웹의 기본), **DNS** (이름을 주소로 바꾸는 창구)
* **양방향 상시 연결:** **WebSocket** (연결을 끊지 않고 주고받는 통화)
* **발행-구독(Pub-Sub) 메시징:** **MQTT** (경량 메시징, IoT에서 주로 쓴다), **AMQP** (작업 큐와 믿을 수 있는 전달, RabbitMQ가 쓴다), **Kafka 프로토콜** (대용량 로그 처리)
* **초경량 IoT:** **CoAP** (저사양 기기용, UDP 위에서 돈다)
* **메시징·프레즌스:** **XMPP** (XML 기반 실시간 메시징과 접속 상태 공유)

**애플리케이션 프로토콜은 API가 아니다. MQTT도 그 갈래 가운데 하나인 애플리케이션 통신 프로토콜(Application Communication Protocol)이다.** 둘을 섞어 쓰면 API와 스택의 관계를 거꾸로 이해하기 쉽다.

* **API:** 프로그램끼리 무엇을 어떻게 요청할지 정해 둔 규칙과 창구다. 메뉴판에 가깝다.
* **애플리케이션 프로토콜(MQTT, HTTP 등):** 데이터를 실제로 실어 나르는 방식이다. 배달 오토바이와 도로망에 가깝다.

[04-application](04-application/)에서 다섯 프로토콜을 모두 직접 구현한다. 브로커와 서버까지 만들어 두었으니 Mosquitto나 aiocoap을 깔지 않아도 된다.

## 4. API — 스택의 맨 위에 달린 문이자 제어판

API는 프로토콜 스택과 대립하는 개념이 아니다. **API는 거대한 통신 엔진에 달아 놓은 조작 핸들이다.**

### 4.1 역할로 본 관계

코드로 통신 프로그램을 만들 때 1층부터 3층까지 로직을 매번 처음부터 짜지는 않는다. 운영체제(OS)가 전송 계층까지 이미 구현해 두었기 때문이다. 4층 프로토콜은 대개 라이브러리가 맡는다. 다만 DNS 이름 풀이처럼 운영체제가 직접 내주는 기능도 있다.

* **프로토콜 스택 = 엔진:** OS 깊숙한 곳에서 패킷을 쪼개고, 주소를 찾고, 유실을 확인하며 데이터를 실제로 날려 보낸다. 기능의 실체가 여기 있다.
* **API = 조작 핸들:** 개발자가 그 엔진을 제어하도록 OS나 라이브러리가 내주는 `connect()`, `send()`, `publish()` 같은 함수다. 명령을 받는 창구다.

### 4.2 계층으로 본 관계

계층 구조로 그리면 API가 어디에 붙는지 분명해진다. 다만 어느 계층을 부르는 API인지에 따라 그 자리가 달라진다. MQTT 라이브러리 API는 4층 위에 얹히고, 소켓 API는 애플리케이션과 3층 전송 계층 사이에 붙는다. 아래 그림은 라이브러리 API를 쓸 때를 보여 준다.

```text
  [ 개발자가 만든 서비스 / 앱 ] (예: 스마트홈 제어 앱)
               │
               ▼
┌──────────────────────────────────────────────┐
│  ▶ API (Application Programming Interface)    │ ◀ 개발자가 잡는 "조작 핸들"
└──────────────────────┬───────────────────────┘
                       │ (API 명령이 하부 스택을 깨운다)
                       ▼
┌──────────────────────────────────────────────┐
│  4층. 어플리케이션 계층 (MQTT, HTTP 등)       │ ──┐
├──────────────────────────────────────────────┤   │
│  3층. 전송 계층 (TCP, UDP)                   │   ├─► [ TCP/IP 프로토콜 스택 ]
├──────────────────────────────────────────────┤   │   (데이터를 실제로 나르는 엔진)
│  2층. 인터넷 계층 (IP)                       │   │
├──────────────────────────────────────────────┤   │
│  1층. 네트워크 인터페이스 계층 (Wi-Fi, 이더넷)│ ──┘
└──────────────────────────────────────────────┘
```

개발자는 API에 한 줄을 적어 '거실 전등 켜기' 메시지를 애플리케이션 프로토콜로 보내라고 명령한다. 그러면 그 명령이 아래 스택을 타고 내려간다. 스택은 그 명령을 TCP 상자에 포장하고, IP 주소를 붙이고, 무선 전파(Wi-Fi)로 날려 보낸다.

[06-encapsulation/peel.py](06-encapsulation/peel.py)가 그 포장을 한 겹씩 벗겨 보여 준다.

### 4.3 자동차로 바꿔 보면

* **프로토콜 스택은 자동차의 구동 체계다.** 엔진, 변속기, 바퀴가 여기에 해당한다.
* **API는 운전석의 페달과 스티어링 휠이다.** 운전자가 실린더의 움직임을 몰라도 페달만 밟으면 구동 체계가 작동해 차가 나아간다.

### 4.4 소켓 API — 가장 널리 쓰는 실례

전송 계층(TCP·UDP)을 조작할 때 사실상의 표준으로 쓰는 API가 **소켓 API(Socket API)**다. BSD 소켓을 POSIX가 규격으로 정했고, 윈도우는 세부가 조금 다른 Winsock을 쓴다.

개발자는 `socket()`, `bind()`, `listen()`, `accept()`, `connect()`, `send()`, `recv()`, `sendto()`, `recvfrom()`, `close()` 함수 열 개로 스택을 다룬다. TCP는 `listen()`, `accept()`, `connect()`로 연결을 맺은 뒤 `send()`와 `recv()`를 쓴다. UDP는 연결을 맺지 않고 `sendto()`와 `recvfrom()`으로 바로 주고받는다. `socket()`과 `close()`는 양쪽이 똑같이 쓰고, 받는 쪽이 포트를 잡는 `bind()`도 마찬가지다.

[03-transport-socket](03-transport-socket/)에서 이 함수를 뼈대로 삼아 서버와 클라이언트를 짜 본다. 그 코드가 [05-api-layers/01-socket-api](05-api-layers/01-socket-api/)의 출발점이 된다.

## 5. 실습을 밟아 가는 순서

폴더는 계층 순서로 번호를 매겼다. 아래 순서는 그 폴더를 밟아 가는 차례다. 1번만 폴더 셋에 걸치고, 2번부터는 항목마다 폴더 하나와 짝을 이룬다.

1. **아래에서 위로 한 번 훑기.** (`01-link-layer`, `02-internet-layer`, 그리고 `03-transport-socket`의 캡처 단계) 프레임과 IP 패킷을 눈으로 확인하고, TCP 연결이 열리고 닫히는 과정을 캡처한다.
2. **소켓 API로 직접 짜기.** (`03-transport-socket`) TCP 에코 서버와 UDP 송수신기를 소켓 API만으로 만든다. 스택을 손으로 만지는 단계다.
3. **애플리케이션 프로토콜을 갈래별로 하나씩 만들기.** (`04-application`) 요청-응답(HTTP), 양방향 상시 연결(WebSocket), 발행-구독(MQTT), 초경량 IoT(CoAP)로 같은 기능을 구현해 견준다.
4. **API 방식을 바꿔 가며 여덟 번 다시 짜기.** (`05-api-layers`) 소켓 → 라이브러리 → REST → GraphQL → gRPC → WebSocket → Webhook → SDK 순으로 올라가며, 계층을 올릴 때 무엇이 편해지고 무엇이 안 보이게 되는지 적는다.
5. **인캡슐레이션 추적하기.** (`06-encapsulation`) API 호출 한 번이 각 계층에서 어떤 헤더를 덧입는지 캡처로 확인한다.
