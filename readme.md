# 🌐 통신 프로토콜 실습

통신 프로토콜을 계층별로 훑고 직접 돌려 보는 실습 모음이다. 특정 프로토콜 하나를 깊게 파지 않고, 하드웨어에서 애플리케이션까지 스택 전체를 아래에서 위로 밟아 올라간다. 맨 위에서는 사람이 만든 소프트웨어를 스택과 이어 주는 **API**까지 다룬다.

---

## 1. 이론(OSI 7계층)과 실제(TCP/IP 4계층)

OSI 7계층은 교과서의 모형이다. 실제 인터넷은 네 층으로 된 **TCP/IP 모델**로 돌아간다. 실습도 TCP/IP 4계층을 기준으로 삼는다.

```text
[ 이론: OSI 7계층 ]                 [ 실제: TCP/IP 4계층 ]             [ 역할과 대표 프로토콜 ]
7. 어플리케이션 (Application) ──┐
6. 프레젠테이션 (Presentation) ──┼─►  4층. 어플리케이션 계층  ───────► 소프트웨어 영역 (HTTP, MQTT)
5. 세션 (Session)             ──┘
─────────────────────────────────────────────────────────────────────────────────────────
4. 전송 (Transport)           ───►  3층. 전송 계층 (Transport) ──────► OS 엔진 영역 (TCP, UDP)
─────────────────────────────────────────────────────────────────────────────────────────
3. 네트워크 (Network)         ───►  2층. 인터넷 계층 (Internet) ─────► 주소·경로 영역 (IP)
─────────────────────────────────────────────────────────────────────────────────────────
2. 데이터 링크 (Data Link)    ──┐
1. 물리 (Physical)            ──┴─►  1층. 네트워크 인터페이스 계층 ──► 하드웨어 영역 (Wi-Fi, 이더넷)
```

'TCP/IP'는 프로토콜 두 개의 이름이 아니다. 인터넷 전체를 떠받치는 **프로토콜군(Suite)**의 이름이다. TCP/IP 모델은 OSI를 줄여서 만든 것이 아니다. OSI와 상관없이 따로 나왔고, 나온 시기도 오히려 더 이르다. 세션과 프레젠테이션이 맡던 일, 곧 연결 상태를 관리하고 데이터 표현을 바꾸는 일은 애플리케이션 프로토콜과 라이브러리가 직접 한다.

## 2. 계층별로 무엇을 실습하는가

| 계층 | 다루는 것 | 실습 |
|---|---|---|
| 1층. 네트워크 인터페이스 | 이더넷 프레임, MAC 주소, ARP, Wi-Fi | 패킷 캡처로 프레임 헤더와 ARP 요청·응답 뜯어 보기 |
| 2층. 인터넷 | IP, ICMP, 라우팅 | `ping`, `traceroute`로 경로 따라가기 |
| 3층. 전송 | TCP, UDP, 포트, 3-way handshake | 소켓으로 TCP·UDP 서버와 클라이언트 만들기 |
| 4층. 애플리케이션 | HTTP, WebSocket, MQTT, CoAP, DNS | 프로토콜마다 최소 클라이언트 짜 보기 |
| 최상단. API | 소켓 API, 라이브러리 API, REST API | 같은 통신을 저수준·고수준 API로 각각 구현해 비교하기 |

## 3. 그래프로 본 IP와 TCP

* **📌 IP = 노드(Node):** 데이터가 닿아야 할 컴퓨터의 위치를 지정하고, 라우터마다 다음에 넘길 곳을 정해 그 컴퓨터까지 패킷을 보낸다. (Host-to-Host)
* **🔗 TCP = 엣지(Edge):** IP가 찾아낸 노드와 노드 사이에 신뢰할 수 있는 가상 파이프라인을 잇고, 흐름과 유실을 관리한다. 정작 데이터가 어느 경로로 가는지는 알지 못한다. (End-to-End)

> **요약:** IP가 노드를 찾아 그리로 패킷을 보내면, TCP가 그 양 끝 사이에 엣지를 잇는다. 그 위에서 HTTP나 MQTT 같은 애플리케이션 프로토콜이 데이터를 실어 나른다.

---

## 4. 애플리케이션 계층 프로토콜의 갈래

4층 프로토콜은 성격에 따라 여러 갈래로 갈린다. 무엇을 나르는지, 얼마나 가벼운지, 누가 먼저 말을 거는지가 그 기준이다.

* **요청-응답(Request-Response):** **HTTP** (웹의 기본), **DNS** (이름을 주소로 바꾸는 창구)
* **양방향 상시 연결:** **WebSocket** (연결을 끊지 않고 주고받는 통화)
* **발행-구독(Pub-Sub) 메시징:** **MQTT** (경량 메시징, IoT에서 주로 쓴다), **AMQP** (작업 큐와 믿을 수 있는 전달, RabbitMQ가 쓴다), **Kafka 프로토콜** (대용량 로그 처리)
* **초경량 IoT:** **CoAP** (저사양 기기용, UDP 위에서 돈다)
* **메시징·프레즌스:** **XMPP** (XML 기반 실시간 메시징과 접속 상태 공유)

**애플리케이션 프로토콜은 API가 아니다. MQTT도 그 갈래 가운데 하나인 애플리케이션 통신 프로토콜(Application Communication Protocol)이다.** 둘을 섞어 쓰면 API와 스택의 관계를 거꾸로 이해하기 쉽다.

* **API:** 프로그램끼리 무엇을 어떻게 요청할지 정해 둔 규칙과 창구다. 메뉴판에 가깝다.
* **애플리케이션 프로토콜(MQTT, HTTP 등):** 데이터를 실제로 실어 나르는 방식이다. 배달 오토바이와 도로망에 가깝다.

## 5. API — 스택의 맨 위에 달린 문이자 제어판

API는 프로토콜 스택과 대립하는 개념이 아니다. **API는 거대한 통신 엔진에 달아 놓은 조작 핸들이다.**

### 5.1 역할로 본 관계

코드로 통신 프로그램을 만들 때 1층부터 3층까지 로직을 매번 처음부터 짜지는 않는다. 운영체제(OS)가 전송 계층까지 이미 구현해 두었기 때문이다. 4층 프로토콜은 대개 라이브러리가 맡는다. 다만 DNS 이름 풀이처럼 운영체제가 직접 내주는 것도 있다.

* **프로토콜 스택 = 엔진:** OS 깊숙한 곳에서 패킷을 쪼개고, 주소를 찾고, 유실을 확인하며 데이터를 실제로 날려 보낸다. 기능의 실체가 여기 있다.
* **API = 조작 핸들:** 개발자가 그 엔진을 제어하도록 OS나 라이브러리가 내주는 `connect()`, `send()`, `publish()` 같은 함수다. 명령을 받는 창구다.

### 5.2 계층으로 본 관계

계층 구조로 그리면 API의 자리가 분명해진다. 다만 어느 계층을 부르는 API인지에 따라 붙는 자리가 다르다. MQTT 라이브러리 API는 4층 위에 얹히고, 소켓 API는 애플리케이션과 3층 전송 계층 사이에 붙는다. 아래 그림은 라이브러리 API를 쓸 때의 모습이다.

```text
  [ 개발자가 만든 서비스 / 앱 ] (예: 스마트홈 제어 앱)
               │
               ▼
┌──────────────────────────────────────────────┐
│  ▶ API (Application Programming Interface)    │ ◀ 개발자가 잡는 "조작 핸들"
└──────────────────────┬───────────────────────┘
                       │ (API 명령이 하부 스택을 깨운다)
                       ▼
┌──────────────────────────────────────────────┐
│  4층. 어플리케이션 계층 (MQTT, HTTP 등)       │ ──┐
├──────────────────────────────────────────────┤   │
│  3층. 전송 계층 (TCP, UDP)                   │   ├─► [ TCP/IP 프로토콜 스택 ]
├──────────────────────────────────────────────┤   │   (데이터를 실제로 나르는 엔진)
│  2층. 인터넷 계층 (IP)                       │   │
├──────────────────────────────────────────────┤   │
│  1층. 네트워크 인터페이스 계층 (Wi-Fi, 이더넷)│ ──┘
└──────────────────────────────────────────────┘
```

개발자는 API에 한 줄을 적어 '거실 전등 켜기' 메시지를 애플리케이션 프로토콜로 보내라고 명령한다. 그러면 그 명령이 아래 스택을 타고 내려간다. 스택은 그 명령을 TCP 상자에 포장하고, IP 주소를 붙이고, 무선 전파(Wi-Fi)로 날려 보낸다.

### 5.3 자동차로 바꿔 보면

* **프로토콜 스택은 자동차의 구동 체계다.** 엔진, 변속기, 바퀴가 여기 해당한다.
* **API는 운전석의 페달과 스티어링 휠이다.** 운전자가 실린더의 움직임을 몰라도 페달만 밟으면 구동 체계가 작동해 차가 나아간다.

### 5.4 소켓 API — 가장 널리 쓰는 실례

전송 계층(TCP·UDP)을 조작할 때 사실상의 표준으로 쓰는 API가 **소켓 API(Socket API)**다. BSD 소켓을 POSIX가 규격으로 정했고, 윈도우는 세부가 조금 다른 Winsock을 쓴다.

개발자는 `socket()`, `bind()`, `listen()`, `accept()`, `connect()`, `send()`, `recv()`, `sendto()`, `recvfrom()`, `close()` 함수 열 개로 스택을 다룬다. TCP는 `listen()`, `accept()`, `connect()`로 연결을 맺은 뒤 `send()`와 `recv()`를 쓴다. UDP는 연결을 맺지 않고 `sendto()`와 `recvfrom()`으로 바로 주고받는다. `socket()`과 `close()`는 양쪽이 똑같이 쓰고, 받는 쪽이 포트를 잡는 `bind()`도 마찬가지다. 실습에서는 이 함수만으로 서버와 클라이언트를 먼저 짜 본다. 여기서 만든 코드가 6절 4항의 출발점이 된다.

## 6. 실습을 밟아 가는 순서

폴더는 계층 순서로 번호를 매겼다. 아래 순서는 그 폴더를 밟아 가는 차례다. 1항만 폴더 셋에 걸치고, 2항부터는 폴더 하나씩 짝을 이룬다.

1. **아래에서 위로 한 번 훑기.** (`01-link-layer`, `02-internet-layer`, 그리고 `03-transport-socket`의 캡처 단계) 프레임과 IP 패킷을 눈으로 확인하고, TCP 연결이 열리고 닫히는 과정을 캡처한다.
2. **소켓 API로 직접 짜기.** (`03-transport-socket`) TCP 에코 서버와 UDP 송수신기를 소켓 API만으로 만든다. 스택을 손으로 만지는 단계다.
3. **애플리케이션 프로토콜을 갈래별로 하나씩 만들기.** (`04-application`) 요청-응답(HTTP), 양방향 상시 연결(WebSocket), 발행-구독(MQTT), 초경량 IoT(CoAP)로 같은 기능을 구현해 비교한다.
4. **API 계층을 바꿔 가며 다시 짜기.** (`05-api-layers`) 소켓 → 프로토콜 라이브러리 → REST 클라이언트 순으로 올라가며, 계층을 올릴 때 무엇이 편해지고 무엇이 안 보이게 되는지 적는다.
5. **인캡슐레이션 추적하기.** (`06-encapsulation`) API 호출 한 번이 각 계층에서 어떤 헤더를 덧입는지 캡처로 확인한다.
