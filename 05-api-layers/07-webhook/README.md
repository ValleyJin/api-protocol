# 07. Webhook — 방향이 뒤집힌다

## 무엇을 배우는가

지금까지 여섯 가지는 모두 클라이언트가 서버를 불렀다. Webhook은 방향이 뒤집힌다.

```
REST      앱 → 서버 : "값 뭐야?"          (앱이 계속 물어야 한다)
WebSocket 앱 ↔ 서버 : 연결을 붙들고 있다  (연결 수만큼 자원을 쓴다)
Webhook   서버 → 앱 : "값 바뀌었어"       (평소에는 아무 연결도 없다)
```

**평소에 아무 연결이 없다**는 것이 Webhook의 강점이다. WebSocket처럼 연결을 붙들지 않고, 폴링처럼 헛되게 묻지도 않는다.

그래서 받는 쪽도 서버여야 한다. 공개된 URL이 있어야 불릴 수 있다. **이것이 Webhook의 가장 큰 제약이다.** 방화벽 뒤의 모바일 앱이나 브라우저는 Webhook을 받을 수 없다. Webhook을 사람이 쓰는 앱보다 서비스끼리 잇는 데 쓰는 까닭이 여기에 있다. GitHub이 CI에 알릴 때, 결제사가 상점 서버에 알릴 때 이 방식을 쓴다.

## 실습

```
python3 source.py                                              # 창 하나
python3 receiver.py                                            # 창 둘
curl -X PUT -d '{"temperature":25.0}' localhost:9600/sensors/living-room   # 창 셋
```

받는 쪽이 등록하고, 값이 바뀌면 보내는 쪽이 부른다.

## 보내는 쪽이 떠안는 짐

REST 서버에는 없던 일이 생긴다.

**재시도.** 받는 쪽이 잠깐 죽어 있을 수 있다. `source.py`가 첫 호출까지 합쳐 세 번 부른다. 세 번 다 실패하면 그 알림은 사라진다. 진짜 서비스라면 큐에 쌓아 두고 한참 뒤까지 다시 보낸다.

**응답을 기다리지 않기.** 받는 쪽을 부르는 동안 값을 바꾼 요청의 응답이 붙들려 있으면 안 된다. `source.py`가 알림을 따로 스레드에서 돌리는 까닭이다.

**중복 처리.** 재시도하면 같은 알림이 두 번 갈 수 있다. 받는 쪽이 같은 것을 두 번 처리해도 괜찮게 짜야 한다. 그래서 실무에서는 알림마다 고유 id를 붙인다.

**받는 쪽이 느리면 내 문제가 된다.** `source.py`는 3초에 끊지만 세 번을 되풀이하니 알림 하나에 9초를 쓰고, 끝내 그 알림을 버린다. 등록된 곳이 천 개면 더 심해진다.

## 받는 쪽이 떠안는 짐 — 서명 확인

내 주소를 아는 누구나 가짜 알림을 보낼 수 있다. "온도가 -300도가 됐다"는 알림을 남이 보내면 어떻게 되는가.

그래서 보내는 쪽이 본문을 공유 비밀키로 HMAC 계산해 헤더에 넣고, 받는 쪽이 같은 계산을 해서 맞춰 본다. GitHub의 `X-Hub-Signature-256`이 그것이다.

```
python3 receiver.py --verify
curl -X PUT -d '{"temperature":27.0}' localhost:9600/sensors/living-room
```

이 실습의 `source.py`는 서명을 **일부러 붙이지 않는다.** 그래서 `--verify`를 켜면 모든 알림이 버려진다.

```
[받는쪽] 서명이 맞지 않아 버린다. 받은 값=(없음)
```

서명 없는 Webhook이 왜 위험한지 그대로 드러난다. 받는 쪽이 확인하지 않으면 아무나 보낼 수 있고, 보내는 쪽이 붙이지 않으면 받는 쪽이 확인할 수 없다.

## 다른 방식과 견주기

| | 평소 연결 | 값이 바뀔 때 | 받는 쪽 조건 |
|---|---|---|---|
| 폴링(REST) | 없다 | 다음 폴링까지 모른다 | 아무 조건 없다 |
| WebSocket | 계속 있다 | 바로 안다 | 아무 조건 없다 |
| Webhook | 없다 | 바로 안다 | **공개 서버여야 한다** |

세 항목 가운데 둘에서 Webhook이 앞선다. 남은 하나가 쓸 수 있는 곳을 크게 좁힌다.

## 직접 확인할 것

- **받는 쪽을 내려 두고 값을 바꾼다.** 보내는 쪽이 세 번 부르고 포기하는 것을 본다. 그 알림이 사라지는 것도 확인한다.
- **받는 쪽에서 500을 돌려준다.** `receiver.py`의 `send_response(200)`을 `500`으로 바꾼다. 보내는 쪽이 세 번 다 부르고 포기한다. 2xx가 아니면 실패로 여기기 때문이다.
- **서명을 붙여 본다.** `source.py`에 HMAC 헤더를 넣어 `--verify`가 통과하게 고쳐 본다. 비밀키를 양쪽이 어떻게 나눠 가질지도 생각해 본다.
