# 01. 소켓 API — 프로토콜을 내가 만든다

## 무엇을 배우는가

가장 낮은 계층이다. HTTP도 MQTT도 쓰지 않고 줄 단위 텍스트 프로토콜을 직접 정한다.

```
GET␊              →  OK 21.0␊
SET 23.5␊         →  OK 23.5␊
(그 밖)           →  ERR unknown command␊
```

여기서 **내가 정해야 하는 것**을 세어 보면, 상위 계층 API가 무엇을 대신 해 주는지 드러난다.

| 정할 것 | 여기서 내가 한 선택 | HTTP라면 |
|---|---|---|
| 메시지 경계 | 줄바꿈 | 빈 줄 + `Content-Length` |
| 오류 표현 | `OK` / `ERR` | 상태 코드 |
| 자료 모양 | 공백으로 나눈 텍스트 | 아무 본문 + `Content-Type` |
| 판본 관리 | 없다 | 헤더로 흥정할 수 있다 |
| 인증 | 없다 | `Authorization` 헤더 |
| 재시도 | 없다 | 클라이언트 몫이지만 관례가 있다 |

빈칸이 많다. 필요해지면 하나씩 내가 만들어야 한다.

## 실습

```
python3 server.py                     # 창 하나
python3 client.py get                 # 다른 창
python3 client.py set 23.5
python3 client.py bench 200
```

`bench`는 연결 하나로 200번 요청한다. 실제로 재어 보면 한 번당 12바이트, 초당 1만 4천 회다. 가장 빠르고 가장 짧다.

## 값과 대가

**값.** 오가는 바이트가 가장 적다. `GET\n` 4바이트에 `OK 21.0\n` 8바이트, 왕복 12바이트다. 같은 값을 REST로 받으면 요청 한 줄에만 78바이트가 들고 여기에 응답 헤더가 더 붙는다. 좁은 망이나 내부 전용 고속 경로에서 이런 선택을 한다.

**대가.** 자기 설명(self-describing)이 없다. 클라이언트가 프로토콜을 미리 알아야 한다. `client.py`에 "GET을 보내면 OK 뒤에 값이 온다"가 코드로 박혀 있다. 서버가 프로토콜을 바꾸면 여기도 고쳐야 한다.

curl로 눌러 볼 수도 없고, 프록시나 캐시가 끼어들 수도 없고, 남이 만든 모니터링 도구가 알아보지도 못한다. HTTP를 쓰면 그 생태계를 그냥 얻는데, 여기서는 아무것도 없다.

## 직접 확인할 것

- **`nc`로 눌러 본다.** `nc 127.0.0.1 9100`으로 붙어 `GET`을 타이핑하면 답이 온다. 프로토콜이 텍스트라 가능하다. 바이너리로 정했다면 이것도 못 한다.
- **프로토콜을 하나 늘려 본다.** `SET`에 단위를 붙이고 싶다고 하자. `SET 23.5 C`로 정하면 예전 클라이언트가 깨진다. 판본 관리를 미리 마련해 두지 않은 대가다.
- **경계를 없애 본다.** 서버에서 줄바꿈으로 자르는 부분을 지우고 `recv()`한 것을 그대로 명령으로 쓰면 어떻게 되는지 본다. 전송 계층을 다룬 03 폴더에서 본 바이트 흐름 문제가 그대로 나온다.
