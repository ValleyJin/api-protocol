# 04. GraphQL — 받을 것을 클라이언트가 고른다

## 무엇을 배우는가

REST와 갈리는 지점은 하나다. **무엇을 받을지 클라이언트가 정한다.**

```
REST      GET /sensors/living-room      →  서버가 정한 필드가 모두 온다
GraphQL   { sensor { temperature } }    →  temperature 만 온다
```

엔드포인트도 하나뿐이다. 자원마다 URL을 파는 REST와 달리 `/graphql` 한 곳에 질의를 적어 보낸다. 그래서 HTTP 메서드도 대개 POST 하나만 쓴다.

## 이 구현의 한계를 먼저 밝힌다

**이 서버는 GraphQL 스펙을 다 따르지는 않는다.** 변수, 조각(fragment), 별칭(alias), 지시어, 타입 검사를 뺀 가르치기용 부분집합이다. 질의를 정규식으로 자르는 조잡한 파서를 쓴다. 진짜 GraphQL 파서는 토큰을 읽어 구문 트리를 만든다.

실무에서는 `graphql-core`나 Strawberry를 쓴다. 여기서 보려는 것은 **"질의가 응답 모양을 정한다"**는 생각 하나다.

## 실습

`compare`는 `03-rest-api`의 서버도 함께 띄워 두어야 REST와 견준다.

```
python3 server.py                     # 창 하나
python3 client.py one                 # 필드 하나만
python3 client.py all                 # 필드 넷 모두
python3 client.py set 24.5            # 뮤테이션
python3 client.py bad                 # 없는 필드를 골라 본다
python3 client.py compare             # REST와 견준다
```

스키마는 `GET /graphql/schema`로도 볼 수 있다.

## 실제로 재어 본 값

```
GraphQL 필드 하나 : 요청 본문 59바이트 → 응답 40바이트
GraphQL 필드 넷   : 요청 본문 70바이트 → 응답 89~90바이트
REST              : 요청에 본문 없음   → 응답 74바이트 (고를 수 없다)
```

값 하나만 필요한 화면에서는 GraphQL이 절반만 받는다. 화면이 많고 필요한 필드가 화면마다 다른 앱에서 이 차이가 쌓인다. REST로 같은 일을 하려면 화면별 엔드포인트를 따로 파거나, 다 받아서 버리거나, 여러 번 부른다.

**대신 요청이 커진다.** 질의를 본문에 실어 보내니 필드 하나만 골라도 59바이트를 먼저 낸다. REST의 GET은 요청 본문이 없다.

## 잃는 것

얻는 것만 보면 안 된다. GraphQL은 REST가 HTTP에 맡겨 두었던 것을 상당 부분 내려놓는다.

| | REST | GraphQL |
|---|---|---|
| 캐시 | GET이라 중간 캐시가 듣는다 | POST라 안 듣는다 |
| 오류 | HTTP 상태 코드 | 본문의 `errors` (상태는 200) |
| 모니터링 | 경로별로 나뉜다 | `/graphql` 하나로 뭉친다 |
| 과부하 방어 | 경로별로 제한을 걸 수 있다 | 질의 복잡도를 따로 재야 한다 |

`python3 client.py bad`를 돌려 본다. 없는 필드를 골랐는데 **HTTP 상태가 200**이고 본문에 `errors`가 들어 있다. REST에서 400이나 404로 걸러지던 것이 본문 안으로 들어온다. 그래서 앞단의 프록시나 알림 도구가 오류를 알아채지 못한다. 오류율 대시보드가 전부 초록인데 사용자만 깨져 있는 상황이 이렇게 생긴다.

## 직접 확인할 것

- **필드 수를 늘려 가며 응답 크기를 잰다.** `client.py`가 내놓는 것은 필드 하나(`one`)와 넷(`all`)뿐이니, 둘과 셋은 `curl -X POST`로 질의를 직접 보내 잰다. 재어 보면 같은 개수에서도 어느 필드를 골랐느냐에 따라 달라진다. 하나 32~41, 둘 51~60, 셋 70~79, 넷 90바이트다. 셋에서도 `{ id temperature ts }`를 고르면 79바이트라 REST의 74를 이미 넘는다. 넘는 자리가 필드 수만으로 정해지지 않는다는 것이 여기서 보인다. 스키마에 있는 필드는 `id`, `temperature`, `unit`, `ts` 넷뿐이라 여기가 끝이다. 다섯째를 넣으면 `Sensor에 그런 필드가 없다`로 막힌다. **이 범위는 서버를 갓 띄운 기본값 21.0도에서 재었다.** 같은 서버에 몇 번을 물어도 크기가 같다. `ts`를 서버가 띄워질 때 한 번 찍고 `set`을 부를 때만 다시 찍기 때문이다. 그래서 `set`으로 값을 바꾸면 범위가 함께 움직인다. `set 0.0` 뒤에는 넷이 89바이트, `set 100.0` 뒤에는 91바이트, `set -100.0` 뒤에는 92바이트다. 이 값들도 `ts` 끝자리에 따라 한두 바이트 움직인다. temperature와 `ts`가 응답에 글자로 실리니 **응답에 찍힌 글자 수**가 그대로 크기에 더해진다. 넣은 값의 자릿수가 아니라 찍힌 글자 수다. 저장소가 소수 한 자리로 줄여 적으니 `set 0.000001`도 `0.0`이 되어 `set 0.0`과 같은 89바이트다. `set 99.96`은 `99.9`가 아니라 `100.0`이 된다. 어느 쪽으로 줄어드는지는 값마다 다르니 넣어 보고 화면에 찍힌 글자를 읽는다. `set 1e15`는 104바이트인데 열 배 큰 `set 1e16`은 `1e+16`으로 짧게 찍혀 91바이트로 오히려 작아진다. 값이 커질수록 응답도 커지는 것이 아니다. **JSON은 숫자도 글자로 싣는다는 것을 여기서 눈으로 본다.**
- **깊은 질의를 만들어 본다.** 이 구현은 한 단계만 다루지만, 진짜 GraphQL에서는 깊이 중첩한 질의 하나로 서버에 과부하를 걸 수 있다. 중첩이 깊어지면 리졸버가 항목마다 따로 조회해 질의 수가 불어나기도 한다(N+1 문제). 그래서 실무에서는 질의 깊이와 복잡도에 제한을 건다.
- **캐시를 확인한다.** REST 서버에 `curl -v`로 두 번 부른다. GraphQL 서버는 POST만 받으니 `curl -v -X POST`에 질의를 실어 두 번 부른다. 그런 뒤 두 응답 헤더를 견준다.
