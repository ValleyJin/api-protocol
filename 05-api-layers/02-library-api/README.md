# 02. 라이브러리 API — 프로토콜을 남이 알아 준다

## 무엇을 배우는가

같은 REST 서버를 세 가지 높이에서 부른다. 서버는 그대로인데 클라이언트 쪽 계층만 바꿔 가며 무엇이 달라지는지 본다.

| 계층 | 내가 쓰는 것 | 내가 하는 일 |
|---|---|---|
| 소켓 | `socket` | 요청 문자열을 손으로 적는다 |
| 표준 라이브러리 | `http.client` | 메서드와 경로를 고른다 |
| 외부 패키지 | `requests` | URL을 적는다 |

## 실습

`03-rest-api`의 서버를 띄워 놓고 돌린다.

```
python3 ../03-rest-api/server.py &
python3 client.py
```

## 실제로 재어 본 값

```
1. 소켓          요청 약  78바이트    내 코드가 4가지 일을 했다
2. http.client   요청 약  86바이트    내 코드가 2가지 일을 했다
3. requests      요청 약 175바이트    내 코드가 1가지 일을 했다
```

계층을 올릴수록 **코드는 줄고 선 위를 흐르는 바이트는 늘어난다.** `requests`가 `User-Agent`, `Accept-Encoding`, `Accept`, `Connection` 헤더를 알아서 붙이기 때문이다. 내가 적지 않은 바이트가 흐른다.

## 어느 쪽이 맞는가

상황이 정한다.

- 사내 서버끼리 초당 수만 번 부른다면 78바이트와 175바이트의 차이가 쌓인다
- 배터리로 도는 센서가 좁은 망에서 부른다면 더 크게 쌓인다
- 사람이 쓰는 앱이 하루에 몇 번 부른다면 아무 차이도 없고, 코드가 짧은 쪽이 낫다

`requests`가 대신 해 주는 것에는 헤더 말고도 연결 재사용, 재시도, 리다이렉트 따라가기, 인코딩 자동 판별이 있다. 이 가운데 하나라도 직접 짜야 한다면 그 순간 계산이 달라진다.

## 직접 확인할 것

실제로 흐르는 바이트를 세려면 캡처를 뜬다. 짐작한 값이 아니라 진짜 값을 본다.

```
sudo tcpdump -i lo0 -A -c 20 port 9200
```

세 방식을 각각 돌리며 요청 줄과 헤더가 어떻게 다른지 글자로 읽는다. `-A`가 본문을 아스키로 찍어 준다. HTTP/1.1이 텍스트 규약이라 이것이 가능하다. gRPC에서는 안 통한다.
