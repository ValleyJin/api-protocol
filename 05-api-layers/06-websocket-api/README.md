# 06. WebSocket API — 한 연결로 요청과 구독을 함께

## 무엇을 배우는가

`04-application/websocket`은 프로토콜 자체를 뜯어보는 자리였다. 여기서는 그 프로토콜 위에 **API를 얹는다.** 프레임 안에 JSON을 넣고 메시지 종류를 내가 정한다.

```
클라이언트 → {"id":1,"method":"get"}
서버       → {"id":1,"result":{"temperature":21.0}}

클라이언트 → {"id":2,"method":"subscribe"}
서버       → {"id":2,"result":"subscribed"}
서버       → {"event":"reading","data":{...}}     값이 바뀔 때마다
```

JSON-RPC 2.0이 바로 이 꼴을 규격으로 정해 둔 것이다. 여기서는 그 뼈대만 쓴다.

### REST와 갈리는 두 지점

**첫째, 요청에 id를 붙여야 한다.** 한 연결에 여러 요청이 떠 있을 수 있어 답이 순서대로 오지 않는다. HTTP는 연결마다 요청 하나를 맞춰 주지만 여기서는 내 몫이다. 게다가 요청의 답과 서버가 먼저 보낸 event가 같은 통로로 섞여 온다. `client.py`의 `call()`이 id로 갈라내는 부분을 읽어 본다.

**둘째, 서버가 먼저 보내는 방향이 있다.** REST에는 없는 방향이다.

## 실습

```
python3 server.py                     # 창 하나
python3 client.py get                 # 다른 창
python3 client.py set 24.5
python3 client.py watch
python3 client.py poll-compare
```

## 실제로 재어 본 값

```
핸드셰이크 282바이트 (연결마다 한 번)
요청 프레임 29바이트 → 응답 프레임 93~94바이트
```

핸드셰이크 282바이트는 기본 포트 9500에서 잰 값이다. 포트 자릿수가 늘면 `Host` 헤더가 길어져 283이 된다. 응답 프레임은 temperature와 `ts`의 자릿수를 함께 따라간다. 기본값 21.0에서는 93과 94를 오가고, `set`으로 자릿수를 늘리면 그만큼 커진다. `set -100.0`이면 96, `set 1e10`이면 103이다. 숫자를 외우지 말고 돌려서 나온 값을 읽는다.

REST의 GET은 요청 78 + 응답 243 = 321바이트였다. 프레임은 둘을 더해 기본값에서 120바이트대이니 요청마다 200바이트 가까이 아낀다. 값의 자릿수를 늘리면 프레임이 커져 아끼는 바이트가 줄어든다. 대신 핸드셰이크를 미리 냈으므로 핸드셰이크를 그 아끼는 바이트로 나눈 만큼 불러야 본전이고, 그 다음 요청부터 이득이다. 지금 값에서는 **두 번째 요청부터** 그렇다. `client.py`가 이 계산을 그대로 찍는다.

**두 가지를 틀리기 쉽다.** 하나는 핸드셰이크를 프레임 크기로 나누는 것이다. 나눌 것은 요청마다 아끼는 바이트다. 또 하나는 나누어떨어지는 지점을 이득이 나는 지점으로 보는 것이다. 그 지점은 본전이고 이득은 그 다음부터다. `client.py`가 `handshake // saved + 1`로 적은 까닭이 이것이다.

### 폴링과 구독

`poll-compare`가 같은 시간 동안 둘을 견준다. 실제로 재어 보면 이렇게 나온다.

```
폴링 3초: 요청 10번, 오간 바이트 1222
구독 3초: 받은 event 1건, 오간 바이트 102
```

**이 3초 동안 값은 한 번도 바뀌지 않았다.** 그런데 폴링은 열 번을 물었다. 열 번 모두 같은 답을 받았으니 전부 헛수고다. 구독은 붙는 순간 현재 값을 한 번 받고 그 뒤로는 조용하다.

값을 바꿔 가며 견주려면 다른 창에서 `python3 client.py set 25.0`을 몇 번 돌린다. 그러면 구독 쪽 건수가 늘어난다. 그래도 바뀐 횟수만큼만 늘어난다는 점이 폴링과 다르다.

**그래도 폴링이 나을 때가 있다.** 값이 하루에 두 번 바뀌고 클라이언트가 십만 개라면, 연결 십만 개를 붙들고 있는 비용이 헛된 요청 비용보다 클 수 있다. 연결 하나가 서버에서 쓰는 것은 메모리만이 아니다. 파일 서술자도 쓴다. 재접속이 몰릴 때의 부담까지 따져야 한다.

## 여기서 안 다루는 것

실무에 쓰려면 더 필요한 것이 있다. 이 구현에는 없다.

- **재접속.** 연결이 끊기면 다시 붙고, 끊긴 동안 놓친 값을 따라잡아야 한다
- **핑·퐁으로 죽은 연결 걸러내기.** TCP가 살아 있어 보여도 상대가 죽었을 수 있다
- **뒤로 밀림(backpressure).** 서버가 미는 속도가 클라이언트가 읽는 속도보다 빠르면 버퍼가 쌓인다
- **인증.** 핸드셰이크 때 토큰을 확인해야 한다

`04-application/mqtt`는 이 가운데 상당 부분을 프로토콜 차원에서 정해 두었다(keepalive, clean session, QoS). 같은 문제를 다르게 푼 답이다.

## 직접 확인할 것

- **id를 지워 본다.** `call()`에서 id 검사를 빼고 첫 응답을 그냥 쓰게 해 본다. event는 subscribe한 그 연결로만 오니, `poll-compare`에서 subscribe를 폴링보다 먼저 걸도록 순서를 바꿔 돌린다. 그러면 `get`의 답 자리에 event가 잘못 들어온다.
- **서버를 내려 본다.** 클라이언트가 어떻게 죽는지 본다. 재접속을 안 만들어 둔 대가다.
- **미는 간격을 줄여 본다.** `server.py`의 `event_loop`에 있는 `time.sleep(0.3)`을 `0.01`로 바꾸고, 다른 창에서 `set`을 쉬지 않고 돌려 본다. 값이 바뀔 때만 밀어 주니 간격만 줄여서는 event가 늘지 않는다.
