# 03. 전송 계층과 소켓 API (3층)

## 무엇을 배우는가

IP는 기기까지 데려다준다. 그 기기 안에서 어느 프로그램에 넘길지는 정해 주지 않는다. 전송 계층이 그 일을 한다. **포트 번호**가 프로그램을 가리키는 주소다.

이 계층에는 성격이 정반대인 프로토콜 둘이 있다.

| | TCP | UDP |
|---|---|---|
| 연결 | 맺는다 (3-way handshake) | 안 맺는다 |
| 도착 보장 | 한다 (재전송) | 안 한다 |
| 순서 보장 | 한다 | 안 한다 |
| 경계 | 없다 (바이트 흐름) | 있다 (데이터그램) |
| 헤더 | 20바이트 이상 | 8바이트 |
| 쓰는 곳 | HTTP, MQTT | DNS, CoAP, 영상 통화 |

### 바이트 흐름이라는 말의 뜻

TCP를 처음 쓸 때 가장 많이 걸리는 곳이다. `send()`를 세 번 했다고 해서 데이터가 상대의 `recv()`에 세 번 나뉘어 들어오지는 않는다. TCP가 보기에 보낸 것은 그저 이어진 바이트 줄이다. 어디서 끊어 읽을지는 **위 계층이 스스로 정해야 한다.** 이것을 메시지 경계라고 부른다.

`tcp_echo_client.py --stream`으로 이 상황을 직접 만들어 볼 수 있다.

04와 05에서 다루는 프로토콜이 이 문제를 저마다 다르게 푼다.

- HTTP: 빈 줄 하나로 헤더 끝을 알리고, `Content-Length`로 본문 길이를 적는다
- MQTT: 패킷 앞에 '남은 길이'를 적는다
- 05에서 소켓으로 직접 만들 저수준 API: 줄바꿈으로 끊는다

**UDP에는 이 문제가 없다.** 보낸 덩어리가 그대로 하나씩 온다. 대신 오다가 사라져도 아무도 모른다. 이 맞바꿈을 실습 6번에서 직접 재어 본다.

### 소켓 API — 스택을 부르는 창구

운영체제는 1층부터 3층까지를 이미 구현해 두었다. 그 엔진을 **소켓 API**라는 손잡이로 부린다. 함수를 부르는 순서는 TCP가 연결을 맺는 순서와 그대로 맞물린다.

```
서버                              클라이언트
socket()                          socket()
bind()      포트를 붙인다
listen()    받겠다고 알린다
                    ◀── SYN ───   connect()
                    ─ SYN+ACK ─▶
                    ◀── ACK ───
accept()    연결 하나를 꺼낸다
recv()      ◀────── 데이터 ────   send()
send()      ─────── 데이터 ────▶  recv()
close()     ◀────── FIN ──────    close()
```

`accept()`가 돌려주는 소켓은 처음 만든 소켓과 다른 물건이다. 처음 것은 계속 문 앞에서 손님을 받고, 새 것이 그 손님 한 명과 이야기한다.

**UDP에는 `listen()`과 `accept()`가 없다.** 맺을 연결이 없으니 받을 것도 없다. 받는 쪽은 `bind()`로 포트를 잡고 `recvfrom()`으로 기다린다. `recv()`가 아니라 `recvfrom()`인 까닭은, 연결이 없어 소켓만 봐서는 상대가 누군지 알 수 없기 때문이다. **보내는 쪽에는 `bind()`도 필요 없다.** `sendto()`를 부르면 커널이 남는 포트를 알아서 붙인다.

## 파일

| 파일 | 하는 일 |

## 실습

### 1. TCP 에코를 돌린다

```
python3 tcp_echo_server.py            # 창 하나
python3 tcp_echo_client.py 안녕       # 다른 창
```

서버가 뜬 채로 `netstat -an | grep 9000`(리눅스는 `ss -tan`)을 돌려 상태가 `LISTEN`으로 나오는지 본다. 클라이언트가 붙어 있는 동안에는 `ESTABLISHED`가, 끊은 뒤에는 `TIME_WAIT`이 보인다.

### 2. 바이트 흐름을 확인한다

```
python3 tcp_echo_client.py --stream
```

`send()`를 세 번 했는데 `recv()`가 한 번에 받는다. 이것이 "TCP는 메시지 경계를 지켜 주지 않는다"는 말의 실제 모습이다.

### 3. 핸드셰이크를 잡는다

`samples/` 폴더는 저장소에 없다. 처음 한 번 만든다.

```
mkdir -p samples
sudo tcpdump -i lo0 -w samples/tcp.pcap port 9000 &    # 리눅스는 -i lo
python3 tcp_echo_client.py 안녕
sleep 1 && sudo pkill tcpdump
python3 parse_tcp.py samples/tcp.pcap
```

서버와 클라이언트를 한 기기에서 돌리면 트래픽이 루프백으로만 흐른다. `-i en0`을 잡으면 한 건도 안 잡힌다.

종료 패킷이 4개가 아니라 3개로 잡히는 일이 흔하다. 받는 쪽이 FIN과 ACK를 한 세그먼트에 묶기 때문이다. 캡처가 잘못된 것이 아니다.

TCP 헤더가 20바이트보다 크게 나오는 것도 확인한다. 옵션이 붙어서다. `parse_tcp.py`는 캡처에 나온 길이를 목록으로 찍는다. 타임스탬프만 붙으면 32바이트다(옵션 10 + 정렬용 NOP 2 = 12). SYN은 더 크다. 이 기기의 루프백 연결을 `getsockopt(IPPROTO_TCP, TCP_CONNECTION_INFO)`로 읽어 보면 타임스탬프와 SACK, 윈도 스케일을 셋 다 협상한다. 세 옵션에 MSS까지 붙으면 옵션 알맹이만 19바이트다(MSS 4 + 윈도 스케일 3 + 타임스탬프 10 + SACK 허용 2). 다만 19는 4의 배수가 아니라 옵션 칸을 20바이트로 채워 쓰니, 네 옵션이 다 붙은 SYN의 TCP 헤더는 적어도 40바이트다. 그보다 커지는지는 운영체제가 NOP를 어디에 몇 개 끼우는지에 달렸다. **이 기기에서는 `/dev/bpf0`이 root 전용이라 캡처로 확인하지 못했다. 그러니 이 숫자를 외우지 말고 자기 캡처에 찍힌 값을 그대로 읽는다.** `tools/make_sample_pcap.py`가 지어낸 표본은 MSS와 타임스탬프만 넣어 36바이트로 나오니, 진짜 캡처와 견주면 차이가 바로 보인다. `06-encapsulation`에서 오버헤드를 셀 때 이 값을 20으로 고정하면 계산이 어긋난다.

### 4. UDP와 견준다

```
python3 udp_receiver.py               # 창 하나
python3 udp_sender.py "안녕"          # 다른 창
python3 udp_sender.py --check         # 받는 쪽 없이 보내 본다
python3 udp_sender.py --burst 1000    # 몰아 보내 본다
```

`--check`는 아무도 없는 포트로 보낸다. 오류가 나지 않는다. TCP였다면 `connect()`에서 바로 거절당했을 것이다.

`--burst`를 쓰고 나서 수신기가 몇 개를 받았는지 세어 본다. **개수가 아니라 읽는 속도가 유실을 가른다.** 받는 쪽이 보내는 속도를 따라가면 100만 개, 1000만 개를 몰아 보내도 한 건도 안 사라진다. 따라가지 못하면 그사이 도착한 것이 커널 버퍼를 채우고, 넘친 뒤에 온 것은 말없이 버려진다. `udp_receiver.py`는 받은 것을 한 건마다 화면에 찍으니 따라가지 못할 쪽이다. 그런데 이 기기에서는 한 쪽에서 몰아 보내고 다른 일을 시키지 않으면 찍으면서도 100만 건을 한 건도 안 잃었다. 찍는 비용이 보내는 속도를 못 따라갈 만큼 크지는 않아서다. 출력을 파일로 보내든 버리든 마찬가지였다. 찍는 줄을 지워 세기만 하도록 고치면 한 쪽에서 1억 개를 몰아 보내도 한 건도 안 사라진다. 다만 보내는 쪽을 넷으로 늘리면 세기만 해도 1000만 개 가운데 몇만에서 수십만 건이 사라진다. 여섯 번 재어 17044건에서 810160건까지 나왔으니 이쪽은 회차마다 크게 흔들린다.

**유실을 보려면 받는 쪽을 실제로 밀어붙여야 한다.** 코어 수의 네 배로 다른 일을 돌려 CPU를 뺏으면 100만 건 가운데 수만에서 수십만 건이 사라진다. **적어 둘 만한 범위가 나오지 않는다.** 무엇을 돌리는지에 따라 2418건에서 575096건까지 벌어졌다. 순수 계산 루프 쉰여섯 개에서 2418~32427건, `dd if=/dev/zero of=/dev/null` 쉰여섯 개에서 59270건, UDP를 쉰여섯 갈래로 함께 쏘는 부하에서 575096건이다. **부하를 섞으면 또 다르다.** `dd`와 UDP를 함께 돌리면 받는 쪽이 아예 못 따라가 버퍼 용량만큼인 8건만 도착했다. 여기 적은 값은 모두 한 번 잰 것이고, 부하의 종류와 섞는 방식에 따라 자리수가 바뀐다. 자기 기계에서 재어 본다. 자기 기계에서 자기 부하로 몇 번 돌려 본다. 디스크와 메모리까지 함께 누르면 더 떨어지는데, 얼마나 떨어지는지는 무엇을 어떻게 누르는지에 달렸다. 보내는 쪽을 넷으로 늘리면 CPU가 한가해도 99만 건대가 된다. 둘로만 늘리면 유실이 거의 없다. 세 번 재어 두 번은 0건이고 한 번은 27건이 사라졌다. **다만 이렇게 미는 것은 번거롭다. 버퍼를 좁히면 같은 일을 적은 건수로 금방 볼 수 있다.** 아래 5번 실습이 그 자리다. 거꾸로 받는 쪽을 2초 늦게 읽도록 고치면 버퍼를 건드리지 않은 기본값(이 기기에서 786896바이트)에서도 10만 개 가운데 4099개만 남는다. 늦추는 시간을 1초로 줄여도, 5초로 늘려도 4099개다. 버퍼가 다 차면 그 뒤로는 더 기다려도 같기 때문이다.

### 5. 한 연결과 여러 연결

```
python3 tcp_echo_server.py            # 창 하나
python3 tcp_echo_client.py A          # 창 둘, 셋에서 동시에
python3 tcp_echo_client.py B
```

둘째 클라이언트가 기다린다. 서버가 한 번에 한 연결만 다루기 때문이다. `tcp_select_server.py`로 바꿔 띄우면 동시에 처리한다.

`select()`는 "이 소켓들 가운데 지금 읽을 것이 있는 소켓을 알려 달라"고 커널에 묻는 함수다. asyncio나 웹 프레임워크도 안쪽에서는 이 물음을 되풀이한다.

### 6. TCP와 UDP를 나란히 재어 견준다

표로 읽는 것과 직접 재는 것은 다르다. 이 폴더의 마무리 실습이다.

```
python3 compare_tcp_udp.py
```

이 스크립트가 서버 둘을 스스로 띄우니 다른 창을 열지 않아도 된다. 같은 일을 두 프로토콜로 시켜 연결 비용, 메시지 경계, 순서, 유실, 처리량 다섯 가지를 잰다. 실제로 돌리면 이렇게 나온다.

| | TCP | UDP |
|---|---|---|
| 연결 비용 | 0.74ms (핸드셰이크 포함) | 0.34ms (없음) |
| 메시지 경계 | send 3번 → recv 1번에 16바이트 (0.2초 뒤에 읽어서 붙어 왔다) | sendto 3번 → recvfrom 3번 |
| 순서 | 50개 그대로 | 50개 그대로 (보장은 없다) |
| 유실 | 347건에서 멈춰 섬. 한 건도 안 버림 | 2000건 중 8건만 도착 (99.6% 사라짐) |
| 처리량 (돌릴 때마다 흔들려 둘을 견줄 수 없다) | 초당 약 1만 8천 회 | 초당 약 1만 2천 회 |

**이 표는 한 번 돌린 결과다.** 다섯 줄 가운데 흔들리는 것과 안 흔들리는 것을 가려 읽어야 한다.

연결 비용과 처리량, TCP가 멈춰 서는 건수는 돌릴 때마다 달라진다. 범위를 적어 두어도 별 도움이 안 된다. 같은 기계에서 스무 번씩 세 차례 재어 보니 멈춘 건수가 409~527건, 403~547건, 358~511건으로 나왔다. 세 번째 범위는 앞의 두 범위 아래로 벗어난다. 스무 번을 재어 얻은 범위조차 다음 스무 번을 담지 못한다. 그러니 이 숫자를 외우지 말고 자기 기계에서 몇 번 돌려 자기 눈으로 본다.

그래도 몇 가지는 스무 번을 돌려도 꼼짝하지 않는다. 메시지 경계가 그렇고, 순서가 그렇고, UDP가 2000건 가운데 8건만 받는 것이 그렇다. 연결 비용은 TCP가 늘 더 컸다. 처리량은 반대로 어느 쪽이 빠른지 회차마다 뒤바뀌어 순위를 읽을 수 없다. `compare_tcp_udp.py`도 그 줄에 순위를 읽지 말라고 찍어 둔다.

사라진 비율 99.6%는 `--count`에 딸려 바뀐다. 50으로 줄이면 84.0%, 20000으로 늘리면 100.0%에 닿는다. 8건보다 많이 보내면 도착하는 건수는 어느 쪽이든 8건이다. 바뀌지 않는 쪽이 8건이고 99.6%는 거기에 딸린 값이다. `--count`를 8 아래로 내리면 보낸 만큼 다 도착해 유실이 0이 된다.

**8이 어디서 나온 숫자인지 따져 보면 뜻밖의 것이 나온다.** **여기서 본문과 데이터그램을 가려야 한다.** 이 글에서 본문은 사용자가 보내는 바이트를 말한다. 코드는 그 앞에 순번 4바이트를 붙여 보내므로 **데이터그램 길이는 본문 + 4**다. 본문 200바이트면 데이터그램이 204바이트다. UDP와 IP 머리글까지 얹으면 선 위에서 232바이트다. 버퍼 2048을 204로 나누면 10.04, 232로 나눠도 8.83이다. 그런데 도착은 8건이다.

본문을 0바이트로 줄여 보면 더 분명하다. 몫으로 셈하면 수백 건이 들어가야 하는데 실제로는 11건에서 멈추고, 본문을 0에서 151바이트로 키우는 사이 그 11건이 꼼짝하지 않는다. 152바이트부터 10건으로 떨어지고, 195바이트에서는 8건, 1000바이트에서는 1건이다. 그사이에 더 잘게 끊기는 단계가 몇 개 더 있다.

**버퍼 바이트를 데이터그램 길이로 나눠서는 건수가 안 나온다.** 수십 바이트짜리 데이터그램 하나가 제 길이의 몇 배를 먹는다. 이 기기에서 4바이트짜리는 48배, 64바이트짜리는 3배였다. 작은 데이터그램만 보내면 버퍼 2048, 4096, 8192, 16384, 65536에서 11, 22, 43, 86, 342건이 들어가고, 아예 건드리지 않은 기본값 786896바이트에서는 4099건이 들어간다.

**커널은 데이터그램 하나마다 자리를 통째로 떼어 둔다.** 그 자리는 길이를 그대로 따라가지 않는다. 큰 버퍼로 재어 보면(버퍼 ÷ 건수) 이렇게 나온다.

| 데이터그램 길이 (본문 + 순번 4) | 한 건이 먹는 자리 |
|---|---|
| 0 | 256바이트 |
| 1 ~ 160 | 192바이트 (고정) |
| 161 ~ 256 | 길이 + 32바이트 |
| 257 ~ 416 | 448바이트 (고정) |
| 417 이상 | 길이 + 32바이트 |

**자리표의 숫자가 어디서 오는지는 두 가지를 재면 보인다.** 커널은 데이터그램 하나마다 버퍼 바이트 몫과 mbuf라는 커널 메모리 조각 몫을 함께 뗀다. 버퍼가 넉넉하면 한 건이 먹는 자리는 둘 가운데 큰 쪽이다. 작은 버퍼에서는 어느 쪽이 먼저 막는지가 길이마다 갈린다. 길이 161~256과 417 이상에서는 바이트 몫이 처음부터 끝까지 막아 늘어나는 간격이 길이+32에서 한 번도 안 바뀐다. 길이 0과 4에서는 둘째 건부터, 300에서는 넷째 건부터, 257과 258에서는 다섯째 건부터 mbuf 몫이 막는다.

**버퍼 바이트 몫은 길이에 32바이트를 더한 값이다.** 그 32 가운데 16은 보낸 쪽 주소 몫이다. 한 건이 들어가는 최소 버퍼를 재어 보면 정확히 길이+16이 나오고, `sockaddr_in`이 16바이트인 것으로 그만큼은 가려진다. 같은 실습을 IPv6(`::1`)로 하면 최소 버퍼가 길이+28로 바뀐다. `sockaddr_in6`가 28바이트다. **주소 체계를 바꾸면 버퍼에 들어가는 건수가 달라진다는 뜻이고, 바이트를 세어 보면 그것이 드러난다.**

**남은 16을 커널이 어느 단계에서 또 매기는지는 가려내지 못했다. 다만 주소와 함께 움직인다.** IPv4에서는 길이를 161부터 65507까지 바꿔도 문턱이 길이+16, 자리가 길이+32로 가외 몫이 16에 고정이다. IPv6으로 바꾸면 문턱이 길이+28, 자리가 길이+60이라 가외 몫도 32로 늘어난다. AF_UNIX 데이터그램에서는 가외 몫이 없다. 보낸 쪽 경로 이름을 2자, 41자, 91자로 바꿔 재도 문턱과 간격이 둘 다 길이+주소 길이(5, 44, 94)로 같다. `recvfrom` 대신 `recv`로 받아도 이 수열이 똑같은데, 커널은 읽는 쪽이 주소를 쓰든 말든 받을 때 넣어 두니 이것으로는 출처를 가릴 수 없다.

**mbuf 몫은 `netstat -m`을 실습 앞뒤로 재면 보인다.** 길이가 1 이상이면 한 건이 mbuf를 세 개 붙들고, 길이가 0이면 네 개를 붙든다. 길이 257부터 2016까지는 거기에 2KB 클러스터가 한 개 더 붙는다. 2017부터는 4KB 클러스터로 바뀌고, 더 키우면 클러스터도 mbuf도 개수가 늘어난다(65507바이트에서 mbuf 열아홉 개에 4KB 열일곱 개다). 다만 그 구간은 바이트 몫이 이미 더 커서 자리표가 달라지지 않는다. 그리고 `sysctl kern.ipc.sockbuf_waste_factor`가 8이다. 커널이 이 몫을 버퍼 바이트로 바꿀 때 8로 나눈다. mbuf 한 개의 크기는 `netstat -mm`이 표 첫 행에 바로 찍는다. 이 기기에서 512바이트다. 같은 표에서 `mbuf_cl 2560`이 `cl 2048`보다, `mbuf_bigcl 4608`이 `bigcl 4096`보다 꼭 512씩 크니 두 쌍이 교차 확인해 준다. **헤더를 뒤지면 엉뚱한 값이 나온다.** SDK의 `arm/param.h`는 `MSIZESHIFT 8 /* 256 */`이라 적어 256을 가리키고 `i386/param.h`도 같다. SDK 안에 512를 적은 헤더는 없는데 실행 중인 커널은 512다. 어느 쪽이 왜 다른지는 사용자 쪽에서 가릴 수 없으니, 지금 실행 중인 커널이 찍어 주는 `netstat -mm`을 믿는다.

이 셋으로 자리표가 그대로 떨어진다. mbuf 한 개가 512바이트이니 192 = 3 × 512 ÷ 8, 256 = 4 × 512 ÷ 8, 448 = (3 × 512 + 2048) ÷ 8이다. **경계 둘은 따라 나온다.** 길이+32가 192를 넘는 첫 길이가 161이고, 448을 넘는 첫 길이가 417이다. **257은 셈에서 나오지 않는다.** 클러스터 없이 들어가는 데이터그램이 256바이트까지라는 것을 따로 재어 얻는다.

**이 자리표로 위 표의 8건이 설명된다.** `compare_tcp_udp.py`는 순번 4바이트를 붙여 204바이트 데이터그램을 보낸다. 한 건이 236바이트를 먹으니 2048바이트 버퍼에는 여덟 건이 들어간다. 본문을 0바이트로 줄이면 데이터그램이 4바이트라 한 건이 192바이트를 먹고 열한 건이 들어간다. 1000바이트로 키우면 한 건이 1032바이트를 먹어 두 건뿐이다.

**다만 작은 버퍼에서는 자리표를 그대로 나눠서 건수를 맞힐 수 없다.** **데이터그램** 257바이트를 2048바이트 버퍼에 넣으면(본문 253바이트다) 자리표의 448로 셈하면 네 건인데 실제로는 여섯 건이 들어간다. **클러스터를 안 잡아서가 아니다.** `netstat -m`으로 세어 보면 작은 버퍼에서도 건당 한 개씩 꼭 잡는다. 두 몫이 늘어나는 간격이 다르기 때문이다. 데이터그램 257바이트 한 건이 들어가는 최소 버퍼가 273이다. 두 건·세 건·네 건은 거기서 **289씩**(길이+32) 늘려야 들어간다(562, 851, 1140). 다섯째 건은 289가 아니라 433을 더한 1573부터다. 그 뒤로 여섯째·일곱째·여덟째가 448씩 늘어 2021, 2469, 2917이다. 큰 버퍼에서는 자리표가 맞고 작은 버퍼에서는 간격이 좁은 쪽이 먼저 막는다. `SO_RCVBUF`를 2의 거듭제곱이 아닌 값으로도, 아주 작은 값으로도 바꿔 가며 직접 재어 본다. 버퍼를 데이터그램 길이+16보다 작게 잡으면 한 건도 안 들어간다. 길이와 같게 잡아도 0건이다. `kern.ipc.maxsockbuf`(이 기기에서 8388608)보다 크게 요청하면 오류 없이 그 값으로 깎인다.

**다만 이 자리표도 외울 것이 아니다.** 운영체제와 판본에 따라 다르다. **외울 것은 건수가 아니다. 넘친 뒤에 온 것을 말없이 버린다는 사실이다.**

**유실 줄이 이 실습의 핵심이다.** 루프백은 선이 깨끗해서 가는 길에 깨지는 일은 없다. 그래도 받는 쪽이 못 따라가면 커널 버퍼가 넘쳐 유실이 난다. 받는 쪽 버퍼를 2048바이트로 좁히는 것은 유실을 만들어 내려는 것이 아니라 그 일을 적은 건수로 금방 보이게 하려는 것이다. 그때 두 프로토콜이 전혀 다르게 반응한다. TCP는 **보내는 쪽을 멈춰 세우고** UDP는 **그냥 버린다**. 보내는 쪽은 버려진 줄도 모른다.

여기서 운영체제가 끼어드는 것도 보인다. `listener`에 `SO_RCVBUF`를 2048로 걸어도 macOS는 `accept`된 소켓의 수신 버퍼를 제 판단으로 키운다(이 기기에서 326640바이트). 그래서 코드가 보내는 쪽의 `SO_SNDBUF`도 함께 줄인다. 소켓 옵션이 명령이 아니라 요청이라는 것을 여기서 확인한다.

**순서 줄은 보장과 결과를 가려 읽어야 한다.** 루프백에서는 UDP도 순서가 지켜지는 일이 많다. 지켜 준다는 약속이 없을 뿐이다. 돌려 보고 "UDP도 순서가 맞네"라고 결론 내리면 안 된다. 일부러 뒤섞으려면 `netem`이나 `dnctl`을 쓴다([`../04-application/coap/`](../04-application/coap/)에 명령을 적어 두었다).

### 이 차이가 4층을 가른다

다섯 가지를 재고 나면 `04-application` 폴더의 선택이 읽힌다.

| 고른 것 | 까닭 |
|---|---|
| HTTP, MQTT → TCP | 받아야 할 것을 다 받아야 한다. 멈춰 서도 버리지는 않는다 |
| DNS → UDP | 질의 하나가 한 통에 담긴다. 늦으면 다시 물으면 된다 |
| CoAP → UDP | 헤더를 아껴야 한다. 대신 재전송을 직접 적는다 |

마지막 줄이 대가를 치르는 모습이다. [`../04-application/coap/`](../04-application/coap/)의 `send_confirmable()`이 TCP가 공짜로 해 주던 일을 손으로 적은 것이다.

## 직접 확인할 것

- **TIME_WAIT은 왜 남는가.** 클라이언트를 끊고 `netstat -an`을 보면 먼저 닫은 쪽, 곧 클라이언트의 임시 포트가 한동안 `TIME_WAIT`으로 남는다. 늦게 도착한 세그먼트가 다음 연결에 끼어들지 않게 하는 장치다. 서버가 먼저 닫으면 같은 상태가 서버 포트에 남아 다시 `bind()`를 막는다. 서버 코드의 `SO_REUSEADDR`은 그때 쓰라고 켜 둔 것이다.
- **임시 포트.** 클라이언트를 여러 번 돌리며 내 쪽 포트 번호가 어떻게 변하는지 본다.
- **순서 번호.** `parse_tcp.py`로 SYN의 순서 번호를 본다. 0이 아니라 무작위 값에서 시작한다. 예측되면 남이 끼어들 수 있기 때문이다.

## 자주 막히는 곳

| 증상 | 까닭 |
|---|---|
| `Address already in use` | 그 포트를 누가 이미 잡고 있다. 내가 띄운 서버일 수도 있고 남이 띄운 프로그램일 수도 있다. `lsof -nP -i:9000`으로 누구인지 보고, 끌 수 없으면 `--port`를 바꾼다. 상태를 `-sTCP:LISTEN`으로 좁히면 `bind`만 하고 `listen`을 안 한 소켓을 놓친다(그냥 `lsof`에는 `(CLOSED)`로 보인다). UDP 소켓은 `-s`가 거르지 않아 그대로 나온다. 포트 번호는 TCP와 UDP가 따로 쓰니 UDP 수신기가 잡은 9001이 TCP 서버를 막지는 않는다. 같은 종류끼리 겹칠 때에만 이 오류가 난다. 서버 코드는 `SO_REUSEADDR`을 켜 두었으니 `TIME_WAIT` 때문은 아니다 |
| 캡처에 아무것도 안 잡힌다 | 한 기기 안의 트래픽은 물리 인터페이스로 흐르지 않는다. `-i lo0`(리눅스 `-i lo`)을 잡는다 |
| 둘째 클라이언트가 멈춰 있다 | 기본 서버는 한 번에 한 연결만 다룬다. `tcp_select_server.py`를 쓴다 |
| UDP를 보냈는데 아무 일도 안 난다 | 정상이다. UDP는 상대가 있는지 확인하지 않는다 |
| 수신기가 받은 건수가 적게 나온다 | 수신기를 `Ctrl+C`로 끝낸다. `kill -9`로 끊으면 아직 찍히지 않고 버퍼에 남아 있던 줄이 함께 사라져 로그 끝줄이 실제보다 적게 보인다 |
| `compare_tcp_udp.py`의 TCP가 안 멈춘다 | 버퍼가 커서 다 들어갔다. `--count`를 올린다 |
