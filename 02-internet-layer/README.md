# 02. 인터넷 계층 (2층)

## 무엇을 배우는가

1층은 같은 랜 안에서만 통한다. 이 계층은 그 경계를 넘는다. 전 세계 어느 기기에든 닿을 수 있게 주소를 매기고 길을 찾는 일을 맡는다.

IPv4 헤더는 옵션이 없으면 20바이트다.

```
 0               1               2               3
┌───────┬───────┬───────────────┬───────────────────────┐
│버전(4)│IHL(4) │    TOS(8)     │      전체 길이(16)    │
├───────┴───────┴───────────────┼───┬───────────────────┤
│        식별자(16)             │FLG│  단편 오프셋(13)    │
├───────────────┬───────────────┼───┴───────────────────┤
│   TTL(8)      │  프로토콜(8)  │    헤더 체크섬(16)    │
├───────────────┴───────────────┴───────────────────────┤
│                   출발지 주소(32)                     │
├───────────────────────────────────────────────────────┤
│                   목적지 주소(32)                     │
└───────────────────────────────────────────────────────┘
```

### 세 가지만 짚는다

**IHL**은 헤더 길이를 4바이트 단위로 적는다. 보통 5라서 20바이트다. 이 값을 읽지 않고 20으로 고정해 파싱하면 옵션이 붙은 패킷에서 어긋난다.

**프로토콜**은 그 위 계층을 가리킨다. 6이면 TCP, 17이면 UDP, 1이면 ICMP다. 1층의 이더타입과 같은 구실이다.

**TTL**은 라우터를 지날 때마다 1씩 줄어든다. 0이 되면 라우터가 그 패킷을 버린다. 길을 잘못 들어 뱅뱅 도는 패킷이 영원히 남지 않게 하는 장치다. `traceroute`는 이 성질을 거꾸로 이용한다.

### IP가 하는 일과 하지 않는 일

IP는 **경로를 미리 정하지 않는다.** 보내는 쪽은 목적지 주소만 적고, 라우터마다 "이 주소는 저쪽으로" 하며 다음에 넘길 곳만 정한다. 홉 단위 전달(hop-by-hop forwarding)이라고 한다. 그래서 같은 목적지로 보낸 패킷이 매번 다른 길로 갈 수도 있다.

IP는 **도착을 보장하지 않는다.** 순서도 지켜 주지 않는다. 중간에서 버려도 알려 주지 않을 때가 많다. 그 일은 위 계층인 TCP가 맡는다. 이렇게 책임을 나눠 둔 덕에 라우터는 단순해지고 빨라진다.

### 체크섬 — 1의 보수 합

IP 헤더에는 체크섬이 붙는다. 셈법은 단순하다. 2바이트씩 잘라 더하고, 넘친 자리를 아래로 돌려 더하고, 마지막에 비트를 뒤집는다.

이 셈법을 고른 까닭이 있다. 받는 쪽이 **체크섬 자리까지 포함해** 2바이트씩 더하고 넘친 자리를 돌려 더하면, 마지막 뒤집기를 하지 않은 그 합이 반드시 0xFFFF가 된다. 값을 새로 구해 견줄 필요 없이 결과가 0xFFFF인지만 보면 된다. 그래서 라우터가 패킷마다 치르는 비용이 아주 낮아진다. TTL이 줄 때마다 체크섬을 다시 구해야 하므로 이 비용이 중요하다.

## 파일

| 파일 | 하는 일 |
|---|---|
| `checksum.py` | 1의 보수 합을 구한다. 자체 검사가 들어 있다 |
| `parse_ip.py` | 캡처에서 IP 헤더를 필드별로 갈라 읽는다 |
| `ping.py` | ICMP Echo를 직접 만들어 보낸다 |
| `traceroute.py` | TTL을 올려 가며 중간 라우터를 드러낸다 |

## 실습

### 1. 체크섬이 어떻게 도는지 본다

```
python3 checksum.py
```

RFC 1071의 예제 값이 맞는지, 실제 IP 헤더에서 체크섬을 다시 구할 수 있는지, 1바이트를 망가뜨렸을 때 검사가 걸러 내는지까지 확인한다.

### 2. ping을 직접 만든다

```
python3 ping.py 8.8.8.8
python3 ping.py example.com -c 5 -s 64
```

`ping` 명령을 부르지 않는다. ICMP 헤더 8바이트에 데이터를 붙여 조립하고 체크섬을 구해 소켓에 넣는다. IP 헤더는 커널이 붙여 준다.

소켓을 여는 방법은 두 가지다. `SOCK_RAW`는 관리자 권한이 필요하고, `SOCK_DGRAM` + `IPPROTO_ICMP`는 macOS에서 권한 없이 열린다. 리눅스는 `net.ipv4.ping_group_range` 설정에 따라 갈린다. 코드는 권한이 필요 없는 쪽을 먼저 열어 보고, 실패하면 `SOCK_RAW`로 넘어간다.

`SOCK_DGRAM`으로 열면 커널이 식별자 필드를 제 것으로 바꿔 버린다. 그래서 코드가 식별자 대신 순번으로 짝을 맞춘다. 운영체제가 중간에 끼어들어 값을 고치는 사례다.

### 3. 경로를 드러낸다

```
python3 traceroute.py 8.8.8.8 -m 20
```

`*`만 나오는 줄이 섞여 나온다. 그 홉이 경로에서 사라진 것은 아니다. 그 라우터가 ICMP를 아예 돌려주지 않거나, 돌아오는 ICMP가 중간에서 걸린 것이다.

### 4. IP 헤더를 뜯어본다

```
mkdir -p samples
sudo tcpdump -i en0 -c 30 -w samples/ip.pcap
python3 parse_ip.py samples/ip.pcap
```

IHL이 5가 아닌 패킷이 섞여 있는지, TTL 값이 출발지마다 어떻게 다른지 훑어본다.

## 직접 확인할 것

- **경로가 바뀌는지 확인한다.** 같은 목적지에 `traceroute`를 여러 번 돌린다. 중간 홉이 달라지면 보내는 쪽이 경로를 정하지 않는다는 사실을 눈으로 확인한 셈이다.
- **TTL 초깃값으로 운영체제를 짐작해 본다.** `ping` 응답의 TTL이 64에 가까우면 macOS나 리눅스에서, 128에 가까우면 윈도우에서 온 것일 때가 많다. TTL은 초깃값에서 출발해 거쳐 온 홉 수만큼 줄어든 채로 도착한다.
- **DF 비트를 살펴본다.** `parse_ip.py`가 DF 비트가 선 패킷을 알려 준다. 이 비트가 서 있으면 라우터가 패킷을 쪼개지 못하고 대신 "너무 크다"는 ICMP를 돌려준다. 경로 MTU 탐색이 이렇게 돈다.

## 자주 막히는 곳

| 증상 | 까닭 |
|---|---|
| 소켓을 못 연다 | 리눅스에서 `sysctl net.ipv4.ping_group_range`를 확인한다. 그래도 안 되면 `sudo`를 붙인다 |
| `traceroute`가 전부 `*` | `ping`은 되는데 이것만 그렇다면 돌아오는 ICMP 타입 11을 방화벽이 막고 있을 수 있다 |
| 응답은 오는데 TTL이 안 보인다 | `SOCK_DGRAM` 소켓은 운영체제에 따라 IP 헤더를 떼고 준다 |
